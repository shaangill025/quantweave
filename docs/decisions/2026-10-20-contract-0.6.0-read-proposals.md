# Project contract 0.6.0: read proposals for owner review

Status: **Proposal.** Nothing here is in the contract, the API or the web client. It
answers owner decision 4 of 2026-10-20 (`docs/decisions/2026-10-20-owner-decisions.md`)
and gives the exact target for decisions 1 to 3. Written against `origin/main`
`930f1c7` and the open PR #126 (`t044-experiment-store-reads`), which serves
listExperiments and readExperiment.

Sources: `openapi.yaml`, the `experiment` and `promotion_receipt` schemas,
`data_dictionary.json`, spec §3 and §11, T008 review (C-02, C-07, C-20, C-21, §5),
`amendments.json`, `project_contract.py`, receipts T044 (with PR #126), T049–T051,
T055, `qw_domain.improvement`, `.release`, `.optimizer_improvement`, and `apps/api`.

## Shared conventions (all three reads)

- `GET` only, membership session (`current_principal`), tenant derived from the
  session, never from the request (C-07). No body, no Idempotency-Key, no audit row.
- Lists are C-02 keyset pages `{items, next_cursor, coverage}` with the `qw_api.reads`
  HMAC cursor (bound to tenant, principal, route and sort key, 1 h), `limit` 1 to 200,
  default 50; a foreign or tampered cursor is 400 `invalid_cursor`.
- Unknown and out-of-scope ids are the same 404 `not_found` (C-07, A-10);
  integrity failures are 409 `integrity`; database errors are 500.
- Numbers are decimal strings (`Decimal`); integers only for counts and schema
  versions. Timestamps are RFC 3339 with an offset, served in UTC.
- Every item carries `coverage` (as `proposal` since 0.4.0). Item reasons are
  `<kind>:<detail>`; page reasons are `<kind>:<id>/<detail>`, at most 300 characters.
  Kinds already in use: `unavailable`, `unknown`, `none`, `blocked`, `deferred`,
  `insufficient`, `rejected`, `evidence`. A value the server cannot attest is null and
  named, never invented or zeroed.
- Expressing new operations: `amendments.json` today can only amend existing schemas
  and request bodies. New paths and schemas need two new keys (`operations`,
  `new_schemas`) handled by `tools/project_contract.py`, and
  `tools/check_contracts.py` must check them (open question Q1). With `enum_add` and
  `all_of` (decisions 1 to 3), that makes four new amendment keys in total.
- `GET /session` (T010, `routes.py`) is served by the API but absent from
  `openapi.yaml`. Read C sits under it, so Q1 must also cover adding `GET /session`
  to the project contract.

## Read A: scorecard and verdict

### Operations

| operationId | Method and path | Query | Response |
|---|---|---|---|
| `readExperimentScorecard` | `GET /experiments/{experiment_id}/scorecard` | none | `experiment_scorecard` |
| `listEvaluationReceipts` | `GET /experiments/{experiment_id}/evaluation-receipts` | `cursor`, `limit` | page of `evaluation_receipt` |
| `readEvaluationReceipt` | `GET /evaluation-receipts/{evaluation_receipt_id}` | none | `evaluation_receipt` |

Sort: `(assessed_at, id)` ascending, so failures and earlier verdicts stay in order
(R084: nothing discarded). `evaluation_receipt_id` is the T044 `verdict_id`, which is
what `experiment.evaluation_receipt_ids` will list.

### Response sketch

`experiment_scorecard` (the frozen protocol's predeclared scorecard, R029):

| Field | Type and constraints |
|---|---|
| `experiment_id` | Id |
| `protocol_id` | sha256 hex; equals `experiment.protocol_id` (protocol content hash) |
| `scorecard_id` | Id |
| `target` | experiment target enum |
| `thresholds` | array of `{metric: Id, direction: at_least\|at_most, bound: Decimal, hard: boolean, control: boolean}`; `control` true for the target's `HARD_CONTROLS` entries |
| `frozen_at` | Timestamp (`Protocol.registered_at`) |
| `coverage` | Coverage |

`evaluation_receipt` (one `Verdict`):

| Field | Type and constraints |
|---|---|
| `id`, `experiment_id`, `candidate_version` | Id |
| `candidate_record_hash`, `protocol_id` | sha256 hex (`Verdict.candidate_hash`, `Verdict.protocol_hash`) |
| `protected_assessor_version` | Id (`Party.version` only) |
| `decision` | `accept_for_review\|reject\|insufficient_evidence\|blocked` |
| `reasons` | array of reason codes (`hard:<metric>`, `goal:<metric>`, `metric_missing:<metric>`, `no_qualifying_trial`, `holdout_reused`, `sandbox_unqualified`, `metrics_mismatch` and so on); empty only for `accept_for_review` |
| `results` | array of `{metric, direction, bound: Decimal, hard, value: Decimal\|null, outcome: passed\|failed\|not_measured}`, one per scorecard threshold, in scorecard order; `value` is **pending Q3** |
| `trial_count`, `failed_trial_count` | integer ≥ 0 |
| `trial_ids`, `failed_trial_ids` | arrays of Id |
| `limitations` | array of codes (`synthetic_only`, `gate_lifted_synthetic`) |
| `assessed_at` | Timestamp |
| `requires_human_promotion` | const true |
| `coverage` | Coverage |

`results` is derived at read time: `Threshold.passes(value)` over the stored scores.
A metric the verdict did not measure is `value: null`, `outcome: not_measured`, and
named `none:results/<metric>`; it is never zero. For `insufficient_evidence` and
`blocked` receipts every `value` is null. Who sees a non-null `value` is Q3.

### Holdout protection (never served)

The protected assessor's holdout data stays out of every response, for every role:

- the T032 plan's promotion window bounds, embargo, `holdout_instruments`,
  `max_promotion_accesses` and dataset contents (only `protocol_id`, a hash, is
  served);
- per-case or per-row results, answer keys, and any trial metric that is not a
  scorecard metric. `assess` copies all of the best trial's metrics into
  `Verdict.scores` (`scores.update(best.metrics)`), so the read must filter to the
  scorecard's metrics;
- the assessor's `actor_id`, `route_id` and `family_id`, and its protected
  configuration (`assessor_config` is a protected key in `improvement._PROTECTED`);
- holdout access records (`access_id`, `seq`, access times).

Reading a verdict creates no holdout access, and `assess` counts only the plan's
first promotion read, so a read cannot buy a second qualifying assessment. Selection
pressure across plans reusing cases remains assessor work (spec §11 rotation; Q3).

### Backing and missing persistence

- Domain: `Scorecard`, `Threshold`, `HARD_CONTROLS`, `Verdict`, `Decision`
  (`qw_domain.improvement`); no new logic beyond the results filter.
- Stored today (PR #126 `experiment_revision`): the verdict id, decision and reasons
  only. **Not stored:** protocols (so no scorecard), verdict scores, trial ids,
  failed trial ids, limitations and `assessed_at`.
- Needed: a protocol store and an `evaluation_receipt` table written only by
  `qw_assessor` (T008 §5). `qw_assessor` has no login path today
  (`check_runtime_role` admits `qw_app` and `qw_worker` only), so this is new
  role and process work. Persistence must store only `assess` output (T044 N3).
- **Cannot be served yet:** anything for code and optimizer targets beyond a
  `blocked` receipt with `sandbox_unqualified` (T007 QUAL17); the data dictionary's
  `environment` and `test_manifest_hash` (no verdict records an environment; served
  null and named `unavailable:environment` until the assessor records one);
  installation-scope experiments (PR #126 refuses that scope; no session holds an
  installation role); a signed receipt (C-20; hash chains only).

### Authorization and tenancy

- Tenant-scope experiments: any member of the tenant (the `Reader` dependency, as
  readExperiment). Forced RLS on `scope_id = tenant_id`.
- Installation-scope experiments: maintainers and installation operators only, once
  those roles exist (Read C). A tenant user sees an installation experiment's
  scorecard and receipts only through a release the tenant is asked to adopt (Q4).
- Producers and assessors are agents with no session or role (T008 §5).

### Requirements

R029/AT029 (a hard violation rejects despite better goals, shown per threshold),
R084/AT084 (failed trials and holdout reuse visible as counts and reasons), R092/AT092
(scorecard and assessor identity are read-only and hashed), R030/AT030 (no approval
field, `requires_human_promotion` true), R028/R033 and AT028/AT033 (all six targets,
code and optimizer shown blocked with reasons), R037/AT037 (V1's verdict inspectable),
R056 and R093 (text outcomes in the governance workspace).

## Read B: release and install history

### Operations

| operationId | Method and path | Query | Response |
|---|---|---|---|
| `listReleases` | `GET /releases` | `cursor`, `limit`, `component` (optional) | page of `release` |
| `readRelease` | `GET /releases/{release_id}` | none | `release` |
| `listDeploymentEvents` | `GET /deployment/events` | `cursor`, `limit`, `component` (optional) | page of `deployment_event` |

`/releases/{release_id}` matches the existing `rollbackRelease` path. `listReleases`
and `readRelease` serve installation-scope releases only, never tenant-scope ones
(R039; `prepare_release` already refuses tenant scope). `listReleases`
sorts by `(installed_at, id)`; `listDeploymentEvents` sorts by ledger order (event
`at`, then sequence), the order `DeploymentLedger` replays.

### Response sketch

`release` (one installed `SignedRelease` and its ledger state):

| Field | Type and constraints |
|---|---|
| `id`, `component`, `experiment_id`, `candidate_id`, `verdict_id`, `rollback_version_id` | Id (`component` is `<target>:<strategy id or target>`) |
| `target`, `change_kind` | experiment target enum; `configuration\|strategy\|application\|optimizer` (`CHANGE_KIND`) |
| `candidate_hash`, `artifact_hash`, `protocol_hash`, `manifest_hash` | sha256 hex |
| `required_approvals` | array of `maintainer_release\|operator_install\|user_strategy_adoption` |
| `compatibility` | `{min_schema, max_schema, writes_schema}` integers ≥ 1 |
| `strategy_version`, `strategy_material_hash` | string or null (non-null exactly for strategy releases) |
| `signature` | `{key_id: Id, algorithm: string, signature_reference: Id, verification: verified\|refused, reasons: array}`; `verify_release` at the database clock against this deployment's trusted keys |
| `install` | `{state: installed\|head\|withdrawn\|paused, installed_at: Timestamp, runnable: boolean, reasons: array}` (`DeploymentLedger.runnable`) |
| `receipts` | array of `promotion_receipt` (the maintainer `release_receipt` and the operator `install_receipt`) |
| `user_adoption_required` | boolean |
| `tenant_adoption` | null, or for strategy releases `{state: not_adopted\|active\|paused, version: string\|null, reasons: array}` for the caller's tenant only (`strategy_state`) |
| `coverage` | Coverage |

`deployment_event`: `{id, kind: install|rollback|pause, component, at: Timestamp,
release_id: Id|null, from_release_id: Id|null, to_release_id: Id|null, reasons:
array, schema_after: integer, operator_id: Id|null, step_up_receipt_id: Id|null,
coverage}`. A rollback never removes the install it withdrew: both events stay
(spec §11 "never edits history").

`experiment_id`, `candidate_id` and `verdict_id` name installation-scope objects that
a tenant cannot read (they would 404). Chosen rule: for tenant members these three
are null and named `unavailable:<field>` (page: `unavailable:<id>/<field>`), so no
response links to an object the caller cannot open; installation roles see the ids.
The three fields are therefore nullable in `release`.

### Hosted versus self-hosted

- **One ledger per deployment.** `DeploymentLedger` holds the events of exactly one
  `Deployment` (`edition`, `operators`, `tenants`). These reads serve the caller's
  own deployment only. The tenant must be in `Deployment.tenants` (`_tenant`), else
  404.
- **Hosted.** Maintainers sign and also install (`authority_scope` maps a hosted
  install to `hosted_maintainer`). Tenants share the deployment, so every tenant sees
  the same installed releases, rollbacks and pauses: these change what runs for them
  (R034). `tenant_adoption` is the caller's own tenant only; other tenants'
  adoptions are never served.
- **Self-hosted.** The operator installs maintainer-signed releases
  (`self_hosted_operator`). The server serves only its own ledger and never fetches
  the hosted maintainer's signing history (R096: no vendor bootstrap call). Releases
  signed but not installed are not known to the deployment; a catalogue of available
  releases is **new domain work** (no distribution store exists).
- **Scopes.** The `release_receipt` is installation scope, the install receipt
  deployment scope; adoption receipts are tenant scope, only in `tenant_adoption`.

### Authorization

- Any tenant member: every field except identities. `operator_id`,
  `step_up_receipt_id`, `approved_by` in receipts and the signature's `key_id` are
  null for tenant members and named `none:<field>` in coverage (Q5).
- Installation operator and maintainer: all fields, including identities, once those
  roles exist. Until then, no session can see them.

### Backing and missing persistence

- Domain: `ReleaseManifest`, `SignedRelease`, `verify_release`, `DeploymentLedger`
  (`Install`, `Rollback`, `Pause`, `head`, `runnable`, `install_receipt`),
  `release_receipt`, `PromotionReceipt.to_wire`, `strategy_state`
  (`qw_domain.release`).
- **No persistence at all** (T051): no tables for signed manifests, trusted keys,
  deployment events or receipts (T008 §5 names `release_receipt` and
  `installation_state` under `qw_release`). Times, operator ids and step-up receipts
  are caller-asserted; step-ups are not checked against T010 records.
- **Cannot be served yet:** any production-verified release (`PRODUCTION_ALGORITHMS`
  is empty until T009 reviews an asymmetric scheme, so every non-test key reads
  `algorithm_not_production`); code and optimizer releases (refused at prepare and
  install, T007); tenant-scope personal-adaptation releases (path not built);
  automatic rollback; post-promotion regressions; strategy adoption of a release
  (`adoptStrategy` is not served). With today's code a real deployment's lists are
  empty with `coverage.status: complete`, which is honest only if the store exists;
  until it does the operations stay unserved (Q2).

### Requirements

R030/AT030 and R099/AT099 (three typed acts on separate receipts), R034/AT034
(install never changes a tenant's adoption; `tenant_adoption` shows it), R039/AT039
(tenant-scope candidates never appear as shared releases), R076/AT076 (signed
promotion and compatible rollback, pauses with reasons), R096/AT096 (self-hosted
history needs no vendor call), R092/AT092 (signature and manifest hash checks shown),
R037/AT037 (V1's install receipt), R056 and R093.

- No token, receipt or signature; no endpoint accepts it as input. Every action

- Only the caller's own classes. The T055 client may hide controls from it and must
  still render the server's refusal.

- Domain: `ApprovalClass`, `MIN_APPROVALS` (`improvement.py`), `authority_scope`,
  `Edition` (`release.py`), `RANK` and step-up checks (`security.py`).

### Hosted versus self-hosted

- Hosted: both release classes map to `hosted_maintainer`; no tenant session holds

- Self-hosted: `operator_install` maps to `self_hosted_operator`, held only by an
  assigned installation operator, never inferred from `tenant_owner` ("self-hosted is

## Decisions 1 to 3: exact target

Implemented by a separate worker after PR #126 merges, as project contract 0.6.0.
None of the reads above is part of this change. The owner decided only the option
labels and option text quoted in the decision record; the mechanics below (reason
forms, the conditional rule, the transition table and re-assessment) are the
implementer's proposed target, for owner review with this document.

### 1. readExperiment item coverage

- `experiment` gains a required `coverage` (`#/$defs/Coverage`). `experimentPage`
  items inherit it through `page("experiment")`; the page keeps its own coverage.
- Item reasons are the stored record's reasons as `<kind>:<detail>` (for example
  `blocked:sandbox_unqualified`, `evidence:synthetic_only`,
  `none:evaluation_receipt_ids`). The page repeats them as `<kind>:<id>/<detail>`.
- `status` is `partial` when there is any reason, else `complete`.
- readExperiment returns 200 with that coverage. The 409 `coverage_required` answer
  and the `withheld:<id>/item` page reason are removed. 404 and 409 `integrity` stay.

### 2. `parent_optimizer_version` nullable

- `experiment.parent_optimizer_version` accepts null.
- It is a string exactly when `target` is `recursive_optimizer` (the candidate's
  `parent_id`, as PR #126 already derives) and null for every other target. This is
  expressed as an `allOf` if/then/else rule, not just a consumer check.
- A null is named `none:parent_optimizer_version` on the item and
  `none:<id>/parent_optimizer_version` on the page. It replaces
  `unavailable:parent_optimizer_version`: the value is known not to apply. The
  amendments `rule` is extended with the item forms `none:<field>` and
  `<kind>:<detail>`.

### 3. States `blocked` and `insufficient_evidence`

`experiment.state` gains `blocked` and `insufficient_evidence`. Derivation in
`improvement.record`:

| Condition | State |
|---|---|
| Verdict `blocked`, or a sandbox target (T007) | `blocked` (sandbox targets were `proposed`) |
| Verdict `insufficient_evidence` | `insufficient_evidence` (was `failed`) |
| Verdict `accept_for_review` / `reject` | `awaiting_review` / `rejected` (unchanged) |
| No verdict: reserved / not reserved or deferred | `authorized` / `proposed` (unchanged) |

`failed` is no longer derived; it stays in the enum for a run failure.

Allowed revisions (replacing the PR #126 state rank and "nothing after a decision"):

| From | To |
|---|---|
| `proposed` | `authorized`, `blocked` |
| `authorized` | `blocked`, `awaiting_review`, `rejected`, `insufficient_evidence` |
| `blocked` | `proposed`, `authorized`, `blocked`, `awaiting_review`, `rejected`, `insufficient_evidence` |
| `insufficient_evidence` | `insufficient_evidence`, `blocked`, `awaiting_review`, `rejected` |
| `awaiting_review`, `rejected` | none in this store (later states belong to T051) |

There is no `authorized` → `proposed` transition: the rank only moves forward from
`authorized`, so a reservation that is lost later re-records as `blocked`, not
`proposed`.

Rules:

- A revision out of `blocked` or `insufficient_evidence` that carries a verdict
  needs a new verdict id. Earlier revisions stay in the chain.
- Protocol, candidate, identity columns and the reservation id are unchanged. A
  re-assessment never resets or re-reserves the budget: whenever the reservation is
  not `reserved` (settled, released or expired), `assess` gives
  `blocked:budget_not_reserved`.
- Sandbox targets stay `blocked` until T007 qualifies.

Proposed, pending Q7 (the owner decided only that `insufficient_evidence` can be
re-assessed once more data exists): re-assessment is a new `assess` run on the same frozen
protocol and candidate. `assess` accepts only the plan's first holdout read, so it can
succeed only if no qualifying read was consumed (for example `no_qualifying_trial`
before any assessor-run promotion trial); otherwise it returns `holdout_reused`. Data
needing a new plan or dataset changes the frozen `plan_digest`: a new protocol and
experiment, never a re-assessment (Q7).

- The other `versions` and `schemas` entries are kept unchanged.
- `changes` gains a `0.6.0:` sentence summarising the three points above.
- `rule` gains the item forms from decision 2.

`tools/project_contract.py` needs two new keys here (four with Q1's `operations` and
`new_schemas`):

- `enum_add` appends values to a property's enum and refuses a value that is
  already present;
- `all_of` appends to the schema's `allOf`, creating it when absent;
- the docstring version becomes 0.6.0.

Other changes: domain `RecordState`, `ExperimentRecord`, `may_follow`; migration
`0027` replacing the 0026 state, decision and optimizer CHECKs and the trigger's state
