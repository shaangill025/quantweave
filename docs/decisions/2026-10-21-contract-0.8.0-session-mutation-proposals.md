# Contract 0.8.0: session and membership mutation proposals (for owner approval)

Status: **approved and implemented.** Owner decision 24 (2026-10-21) approves all
four mutations. Decision 25 resolves the checker conflicts with per-operation
`sensitive_fields` entries and the `unauthenticated_login` and `no_content`
exemptions. Decision 26 has the role change return the stored `display_name` and
reuse the list's `Membership` item; this replaces the null option in section D.
Project contract 0.9.0 implements all three. The rest of this document is the
proposal as it was presented.

## What I checked first

The spec's `docs/spec/contracts/openapi.yaml` has no `/session*`, `/login`,
`/logout`, `/auth*` or `/memberships*` path. No operationId or description mentions
login, step-up or membership. Its only session artifact is the `sessionCookie`
security scheme. So these are real gaps, not a path mismatch between server and
contract. Each operation below mirrors `apps/api/src/qw_api/routes.py` and
`security.py` at c19646b.

## How an approval becomes an entry

An entry in `mutations` is `{"method", "path", "operationId", "decision"}`. The
`decision` is `YYYY-MM-DD#N`. `tools/check_contracts.py` rule 6 accepts the entry
only when section N of `docs/decisions/YYYY-MM-DD-owner-decisions.md` has two lines:
a `Selected label:` line, and a dedicated line of exactly this form:

    Approves: `METHOD /path` (`operationId`)

A decision can approve several operations, one `Approves:` line each. Text anywhere
else, such as the question, the option text or a rejected "Not '...'" option, never
approves anything. Decision 15 has no `Approves:` line, so it cannot be cited. The
decisions file has no integrity check beyond the owner's review of its diff. An entry that matches no amended operation fails. A listed mutation
still has to pass rules 1, 2, 3 and 7 and all of rule 6. A broker or trading
mutation can never be amended. The checker has no way to waive a rule, so the
conflicts below need the owner to pick an option before any entry can pass.

## Conflicts with the current checker (owner choice needed)

| Rule | Conflict | Affected |
|---|---|---|
| 7 | `X-CSRF-Token` (required by rule 2) contains `token`. An amended mutation can't pass without a `sensitive_fields` entry for that header. | B, C, D |
| 7 | The request body field `password` | A, C |
| 2 | Login has no session, so it has no CSRF token. It sends no Idempotency-Key, by design (T010: each response carries a fresh session token). | A |
| 6 | Security must be exactly `sessionCookie`. Login is unauthenticated (`security: []`). | A |
| 6 | Response keys are only 200, 201, 202 and `default`, and every 2xx is `application/json`. Logout returns `204` with no body. | B |

Options per conflict: (1) a per-operation `sensitive_fields` entry that cites the
approving decision (works today, no checker change); (2) a narrow, reviewed checker
exemption: rule 7 skips exactly `X-CSRF-Token` (`in: header`, `required: true`), and
rule 6 accepts an explicit `login` entry with `security: []` and no rule-2 headers,
plus `204` with no content for an explicitly listed operation; (3) change the server
(for example, logout returns 200 with a body). Recommendation: option 1 for
`password` and `X-CSRF-Token`, option 2 for login's security and headers, and option
2 for logout's 204. Changing the server would break the UI's logout handling for no
security gain.

## A. `POST /session`: `createSession` (login)

- Security: none (`[]`). Origin/Referer allowlist (app middleware). No CSRF and no
  Idempotency-Key. The per-address throttle runs first, then the per-account one.
- Request body (`application/json`, required). Strict, so unknown fields are 400:

  ```json
  {"type": "object", "additionalProperties": false, "required": ["login", "password"],
   "properties": {
     "login": {"type": "string", "pattern": "^[a-z0-9][a-z0-9._@-]{0,127}$"},
     "password": {"type": "string", "minLength": 1, "maxLength": 1024}}}
  ```
- `201`: `#/components/schemas/session` (the 0.7.0 readSession schema, unchanged).
  Headers: `Cache-Control: no-store`; `Set-Cookie: __Host-pi_session=<token>;
  HttpOnly; Max-Age=<session_ttl>; Path=/; SameSite=strict; Secure`.
- `default`: Problem. 401 `invalid_credentials` (the same response whether or not the
  login exists), 429 `too_many_attempts` with `Retry-After`, 400 `invalid_request`,
  403 `origin_rejected`, 413 `payload_too_large`.

## B. `DELETE /session`: `revokeSession` (logout)

- Security: `sessionCookie`. Headers: `Idempotency-Key` (required,
  `^[A-Za-z0-9_-]{16,128}$`) and `X-CSRF-Token` (required).
- No request body.
- `204`: no content. Headers: `Cache-Control: no-store`;
  `Set-Cookie: __Host-pi_session=""; Max-Age=0; Path=/; ...` (clears the cookie).
- `default`: Problem. 401 `unauthenticated`, which is also what a retry gets once the
  session is revoked (the session check runs before the idempotency replay), 403
  `csrf_failed` or `origin_rejected`, 400 `invalid_idempotency_key`.

## C. `POST /session/step-up`: `stepUpSession`

- Security: `sessionCookie`. Headers: `Idempotency-Key` and `X-CSRF-Token` (both
  required). Throttled like login.
- Request body (required, strict):
  `{"type": "object", "additionalProperties": false, "required": ["password"],
  "properties": {"password": {"type": "string", "minLength": 1, "maxLength": 1024}}}`
- `200` (`application/json`, no-store), a new schema `step_up`:
  `{"type": "object", "additionalProperties": false, "required": ["step_up_at"],
  "properties": {"step_up_at": {"$ref": "common.schema.json#/$defs/Timestamp"}}}`.
  A retry with the same key on the same session replays the recorded body without
  checking the password again. The request HMAC leaves out the password.
- `default`: Problem. 403 `reauthentication_failed`, 401 `unauthenticated`, 429
  `too_many_attempts`, 409 `idempotency_key_reused` (another session or payload), 400
  `invalid_idempotency_key`.

## D. `PATCH /memberships/{user_id}`: `changeMembershipRole`

- Security: `sessionCookie`. Needs the `tenant_owner` role and a step-up within the
  window (401 `step_up_required`). Path parameter `user_id`
  (`{"type": "string", "format": "uuid"}`). Headers: `Idempotency-Key`,
  `X-CSRF-Token` and `If-Match` (exact `"N"`; 428 `if_match_required` when it is
  missing, 412 `version_mismatch` when it is stale).
- Request body (required, strict):
  `{"type": "object", "additionalProperties": false, "required": ["role"],
  "properties": {"role": {"type": "string", "enum": ["tenant_owner", "tenant_member"]}}}`
- `200` (`application/json`, no-store, `ETag: "N"`), a new schema `membership`:
  `user_id` (uuid), `role` (enum above), `version` (integer, at least 1) and
  `display_name`. **The server always sends `display_name: null` here.** The list read
  sends the stored name. Owner choice: document it as `{"type": "null"}` to mirror
  the server, or change the server to return the stored name and reuse the
  `listMemberships` item schema.
- `default`: Problem. 403 `forbidden` or `self_promotion`, 404 `not_found` (a
  foreign id gives the same 404), 409 `last_owner` or `idempotency_key_reused`, 412,
  428, 401.

None of these touch a broker, account, connection, order or money movement. Rule 1's
surface and verb patterns don't match any proposed path or operationId.
