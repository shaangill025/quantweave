## Owner decisions recorded (interpretations, open to review)
1. **`review_at` and `needs` (contract deviation, conservative reading).** The request `WatchlistEntry` is closed (`additionalProperties: false`) and has no `review_at` or `needs`. The response entry requires `review_at`, as a string or null. Spec §2 and §13 say an entry has a review date and a per-symbol monitoring mode. The routes follow the closed contract and do not extend it:
   - A request carrying `review_at` or `needs` is refused with 400.
   - A new entry gets `review_at: null` and the domain's default `needs` (`realtime_exchange_limited`).
   - An update keeps the stored values of both.
   - `review_at` is always served (null). `needs` is stored and never served.
   - Setting either needs a project-contract amendment, which the owner has not approved. Until then, review-date alerts cannot be set through the API.
2. **If-Match on addWatchlistEntry: contract-conformant, not a deviation.** The contract declares no If-Match here, so it is optional. One that is sent is honoured (412 when stale or malformed). Without one, the store uses the latest revision under the exclusive tenant lock. The domain's `entry_exists` rule still prevents an add from overwriting an entry. Replays are keyed on the Idempotency-Key and body only. Both cases are tested.
3. **Instrument existence.** No spec text requires an instrument registry check, and the repository has no instrument table. The domain rule applies: a canonical `InstrumentId` UUID. An entry proves nothing about ownership and touches no holdings.
4. **Conditions.** All 8 contract operators pass schema validation. The domain then refuses metrics and operators it cannot evaluate deterministically (422) rather than storing a rule that could never fire.
5. **Bounds.** The contract sets no bounds; the limits above and 500 entries per list are this increment's choice, because every revision stores a full snapshot.
6. **Status codes.** A stale or malformed If-Match is 412, though the OpenAPI text says 409. This is a known deviation, applied the same way in T010, T019, T020 and T024 increment 2. Add returns 200, as the contract declares.
7. **`add_entry` replay.** Priority is held to 0..100 by the domain `Entry`, which every stored entry passes through. The domain does not require the default `needs` on an add, so replay does not check it; only the routes set the default. For `update_entry`, replay requires the stored `review_at` and `needs` to equal the prior entry's, because the store always keeps them.

A rename keeps the entries, and the tombstone repeats them. Entry actions on a deleted list are `not_found`.
- **Stored form.** The stored JSON is compared with a hand-written dict, not with `entry_json`.
- **Idempotency.** Each of the three actions replays when the request is the same. The same key is refused when any of these differ: thesis, priority, conditions, tags, invalidation text or instrument. For update and remove, it is also refused when the expected revision differs, or (at the API) when the If-Match differs; both are tested. Refusals hold after the idempotency record is purged. An add with the same key replays whatever its If-Match: `"2"`, none, or `"1"` after later revisions. Another principal's same key writes a new revision.
- **Add without If-Match.** The add takes the latest revision (the store goes from 5 to 6; at the API, from 2 to 3). With If-Match, a stale `"2"`, `"01"` or `W/"1"` is 412, and the current one is accepted.
- **Bounds.** At the API, 17 conditions, 33 tags and 9 values are 400. 16 conditions and 32 tags are accepted. 8 values pass the bound and are refused by the domain with 422, because a condition needs 1 or 2 values. A 422 carries empty `field_errors`: the domain's refusal is not mapped to a field.
- **Golden hashes.** A SYNTHETIC 0022-era create and rename, with no instrument, have hard-coded SHA-256 values. Each was computed outside `revision_hash` from hand-written canonical JSON. A change that alters hashes of existing rows fails this test.
- **Kept fields.** A re-hashed `update_entry` row whose entry has `needs: delayed`, while the prior entry had the default, is `integrity`.
- **Entry limit.** With the limit monkeypatched to 1, a second add gives `entry_limit` and an update still works. The 0023 CHECK is tested directly: 501 entries are refused and 500 accepted, an entry action without an instrument is refused, and a list action with one is refused.
- **Tampering (re-hashed, so only the replay catches it).** Each of these is `integrity` on load, page and write:
  - a priority stored as text;
  - a missing `needs`, or an extra key;
  - unsorted entries;
  - a second entry changed by an add;
  - a target instrument absent from the snapshot;
  - a non-canonical `review_at` (`+00:00`), or an `eq` condition;
  - `values` stored as a string;
  - a list renamed by an entry action;
  - an add relabelled as a remove;
  - an entry action carrying a forged list description.
  - Control: a canonical non-null `review_at` with `needs: delayed` loads, and a later update keeps both.
- **Edits caught only by a specific check.** A no-op update re-pointed at another instrument without re-hashing is caught only by the hash. A rename that names an instrument, with the 0023 constraint dropped in the test's own database, is caught only by the adapter check.
- **API.** 428 for update and delete; 412 for all three. Contract-closed `review_at` and `needs`, priority 101 and `true`, NUL, and a missing `tags` are 400. Uppercase instrument, `eq` and `between 2 1` are 422. Path/body mismatch is 400. An unknown entry is 404. Tenant B gets the same "No such watchlist." 404 on add, update and delete, and on an unknown list. A tampered entry gives 409 `integrity` on read and delete, without echoing the forged text. Every response is validated against the project-contract `watchlist` schema.
- **AT057.** The reads-test journal (10 units bought, hand-computed 9492.55 CAD ledger cash) is seeded. After adding, updating and removing an entry, `readSnapshot` is identical. The store still imports nothing from the journal, postings, imports or proposals, and the table's foreign keys are still exactly membership and session.

# Increment 4: a settable `review_at` (project contract 0.5.0)

Status: In progress. `review_at` can now be set on add and update. The filing-arrived condition, the persistent alert book and the UI remain.

## Scope and authority
- Owner decision 2026-10-15 (docs/decisions/2026-10-15-owner-decisions.md, decision 3): `review_at` is an optional, nullable field on the request `WatchlistEntry` (addWatchlistEntry, updateWatchlistEntry); `needs` stays server-derived. This settles increment 3 gap 1 for `review_at`. Project contract 0.5.0 (`contracts/amendments.json` `requests`, `tools/project_contract.py` `request()`) is in the same change, together with the confirmation of 0.3.0 and 0.4.0 and the If-Match 412/428 convention.

## Changes
| Path | What |
|---|---|
| `packages/adapters/src/qw_adapters/sql/0024_watchlist_review_at.sql` (new) | `review_at_set boolean NOT NULL DEFAULT false`, with a CHECK that only an `update_entry` row may set it, plus a qw_app column grant. The default fills existing rows without an UPDATE, so the append-only triggers are not involved. |
| `packages/adapters/src/qw_adapters/watchlist_store.py` | `update_entry(..., review_set)` replaces `review_at` (null clears it) only when the request set it, and otherwise keeps it. `needs` is always kept. The flag is stored, and `revision_hash` covers it only when true, so 0022- and 0023-era hashes are unchanged. Replay of an `update_entry` row still requires the prior `needs`. It also requires the prior `review_at` unless the row's flag is set, and the flag is refused on any other action. Key replays also match `review_at` (add, and an update that set it) and the flag, so the same key with another `review_at`, or with the field omitted where it had been sent, is `idempotency_key_reused`. |
| `apps/api/src/qw_api/watchlists.py` | `WatchlistEntry.review_at: str \| None`, optional. It is validated by `parse_instant` (C-05: an explicit offset, not `-00:00`, a real date, in UTC range) and stored and served in UTC `Z` form. Whether it was set comes from the body's fields-set. The idempotency payload uses `exclude_unset`, so an omitted `review_at` and an explicit null are different requests. `needs` is still refused (the model is closed). |
| `packages/adapters/tests/test_watchlist_store.py`, `apps/api/tests/test_watchlists_api.py` | 7 new store tests (10 cases with parameters, one an upgrade from 0023), `_rehash` passes the flag, and the `run` helper forwards keywords. One new API test. The increment-3 bad-body case `review_at: null` (now valid) becomes `review_at: "2026-11-02"`. |

Why a migration. The replay must tell whether a stored update row's request set `review_at`, and nothing in the 0022/0023 row records that. The entries snapshot is re-encoded exactly, so a per-entry marker would persist into later snapshots, and a new action name would need a CHECK change anyway. The safest representation is an explicit, hashed, per-row flag that defaults to the old rule ("kept"). A re-hashed forger who also sets the flag can change `review_at`, just as such a forger can change any editable field: that is the hash-only limit already recorded (increment 2, gap 4).

## Negative/adverse cases (SYNTHETIC)
- **Behaviour (store and API).**

The contract `request("WatchlistEntry")` refuses all of these except `-00:00`, which RFC 3339 allows and C-05 forbids. `needs` is still 400.
- **Idempotency.**
