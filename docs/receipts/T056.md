## Negative/adverse cases (SYNTHETIC)
- **Minimal payload.** A proposal (buy 80 at 50, 4000 CAD, acct-1), an alert ("close 99.5 -> 100.25") and a risk pause are rendered for email and push. Title and body contain no quantity, amount, price, currency, side, account, instrument, proposal, watchlist, rule or pause id, tenant, user or address, and no digit at all. The link is exactly `/notifications/ntf-<32 hex>`.
- **Late notification.** One resolver is built at AT and reused. Opened at AT+1 min, the proposal is `active` and actionable. At AT+31 min it is `expired`, not actionable, with current version `1:expired` and event age 31 min; also at AT+45 min. The proposal's events are unchanged, so opening never acts.
- **Superseded, missing, mismatched.** A revised proposal opens its version-1 notification as `superseded` (current `2:candidate`). A missing object opens as `unavailable`. `subject_mismatch` is raised for: another proposal; forged versions `3:active`, `x:active` and the empty string; a job-category subject with the proposal's id; another tenant.
- **Sending is not reading.** Email and push are delivered, yet `seen_at` stays empty, including after a feed listing. The first open sets it, and a later open keeps the first time.
- **Dedupe and retries.** An outbox redelivery returns the original record, `created_at` and `trigger_at`. A trigger 6 min later creates a feed item but its sends are `coalesced`; one 10 min later queues both channels.
- **Delivery state.** Rejected, rejected, accepted gives 3 attempts and `delivered`, accepted 33 s after the trigger, with `created_at` unchanged (R067). A transport exception gives `unknown`/`transport_error` (its text is not stored); a non-enum result gives `unknown`/`unrecognised_result`; both are final. Also refused: `not_retryable` after delivery or `unknown`, `attempts_exhausted`, `time_order`, and `no_delivery` for another user or tenant.
- **Re-check at attempt.** No message is sent and the delivery closes (`failed`, 0 attempts, then `not_retryable`) when, after queueing, push is revoked, push is opted out, email becomes unverified or absent, the category is muted, or the push subscription expires at the attempt time.
- **Quiet hours.** America/Toronto, windows 22:00-07:00 and 12:00-13:00:
  - a signal at 03:00 EDT is deferred to 07:00 EDT, and an earlier attempt is refused;
  - start is inclusive and end exclusive; DST is handled (23:00 EST in December);
  - chained windows 22:00-07:00 and 07:00-08:00 end at 08:00;
  - refused: equal start and end, `7:00`, `24:00`, an unknown timezone, a list instead of a tuple, and windows covering the whole day.
- **Safety (D1).** Risk-pause email and push are not deferred by quiet hours, and a second pause, or a new version of the same pause, inside the window is not coalesced. An alert at the same time is still deferred.
- **Validation.** Refused email addresses: a CRLF `Bcc:` injection, a space, two `@`, no dot in the domain, a local part over 64 characters, over 254 characters in total, and non-ASCII. Refused endpoints: a CRLF, no host, a space, `ftp://`, DEL, over 2048 characters. Also refused: non-bool flags (`"no"`, `"false"`, `1`), a list or untyped `muted`, an unknown permission, a short `id_key`.
- **Atomic submit, resolver errors, isolation.** An exception mid-decision stores nothing, and a retry creates the record with both deliveries. A failing resolver lists items as `unavailable` in the feed; `open` raises and records no `seen_at`. Opening before creation is `time_order`. Other users get `not_found`, and another tenant's signal or recipient is refused. A different `id_key` gives a different id.

### Decisions (open to review)
- **Keyring.** `qw_adapters.notification_store.Keyring(active, seal_keys {kid: key}, id_key)`. It lives in the adapter so qw_app and the qw_worker producer build the same object from operator configuration (the worker has no notification code yet; the consumer is remaining work). Every key is bytes of at least 32 bytes, like `secret_key`. Kids match `^[a-z0-9][a-z0-9_.-]{0,63}$`. The active kid must have a key. All keys must be distinct, and `seal_keys` is frozen. `repr` hides the keys.
- **Settings.** The new field is `notification_keys: Keyring | None = None`. A keyring that contains `secret_key` (as a seal key or as the id key) is refused. When the field is unset, `GET /notifications` returns 503 `notifications_unconfigured`. It never falls back to `secret_key`.
- **Seal rotation.** Each row is sealed under the active kid and stores that kid in `seal_kid`. The kid is also bound into the HMAC body. Each row is verified under its own kid, so after rotation the old kids still verify. A kid that is retired, unknown or missing fails closed (`integrity`). Seals are compared with `hmac.compare_digest`; timing behaviour cannot be asserted by a functional test, so replacing it with `==` survives the suite (see Mutants).
- **The id key is a separate, stable key, not part of the seal keyring.** The record id is three things at once:
  - the dedupe identity (the UNIQUE dedupe key maps to it);
  - the primary key that every child row references;
  - the `/notifications/<id>` link sent by email.

  Rotating it would make a redelivered signal produce a different id. That breaks deduplication, sent links and the stored-id recompute, so it never rotates.
  
  A keyed id was kept over a public per-install salt. With a public salt, anyone who knows the tenant, user and object ids could compute an id. Authorisation still protects the records, but the key also keeps link ids from being linkable.
  
  If the id key leaks, ids are exposed but integrity is not, because every row seal covers the id. A future id-key change would need a new id version, which is out of scope here.
- **Legacy (0017) rows fail closed.** They have no kid, and their seals and ids came from the `secret_key` derivation, which is no longer accepted. Nothing is deployed, so no `legacy-secret-key` verifier was added.
- **0018.** It adds a nullable `seal_kid` (format CHECK) to all four sealed tables, plus a `NOT VALID` NOT NULL check: new rows must carry a kid, and legacy rows stay as recorded. It also grants qw_worker `INSERT (seal_kid)` on `app.notification`. The other tables already have table-level grants.
- **Per-row isolation.** The contract `Notification` item needs an `id`, an `object_id` and a channel. Each of those is content of the failing row, so the API cannot emit a placeholder item without serving or inventing them. Instead:
  - `page` returns the failing record's rows with `item = None`, and the other records are still served;
  - the API leaves those rows out, and coverage becomes `partial` with `unavailable:notification_record/integrity`;
  - the bad record's id, object and state never appear in the body;
  - `load` of that record still raises `integrity`;
  - a database error still fails the page, now as 500 `internal_error`.
  
  Rows from a failing record still use their keyset slots, so the cursor moves past them.

### Decisions (open to review)
- **External channels: refused, fail closed. This is an OWNER DECISION.** The owner has not yet decided whether enabling email or browser push needs step-up authentication, and no transport exists. So `email: true` or `browser_push: true` gets 422 `external_channel_unavailable`, with the neutral detail "External notification channels are not available." Clients are not told about the owner decision. The store refuses it before writing. 0020's `CHECK (NOT email)` and `CHECK (NOT browser_push)` refuse it in the database too. Allowing it later needs that decision, a migration and a transport.
- **If-Match.** The repository uses the T010 form `"N"`. A missing header gets 428. A stale header gets 412 `version_mismatch`, and so does a malformed one (`W/"0"`, `*`, a list, leading zeros). The openapi text says a stale value returns 409. This deviation is the one T019 and T020 already recorded, kept so every route behaves the same; the owner may overrule it.
- **No read operation.** The contract defines no GET. When nothing is recorded, the user is at revision `"0"`, which is the domain defaults (in-app on, email and push off, UTC, no quiet hours, redacted). The first PATCH sends `If-Match: "0"`. Every 200, replays included, carries the ETag of the revision its own request recorded (`by_key`), never the current one, so a replay cannot hand out a newer ETag than its body.
- **Revisions.** Every successful PATCH appends revision N+1, even when the content is unchanged. An Idempotency-Key is also recorded on its revision (UNIQUE per user). After the T025 purge of idempotency records, the same request returns its original revision without writing an audit event (`set_preferences` reports that it wrote nothing), and any other request is 409 `idempotency_key_reused`. The ETag lookup runs after the idempotency transaction, so a revision failing verification there gives 409 `integrity`, never a 500.
- **Scope.** A user can only set their own preferences: the session user, under any membership role. No path or body field names a user or tenant, so the "same 404 for unknown and foreign ids" rule has nothing to apply to. Isolation comes from RLS plus the user filter, and the tests check it.
- **Validation.** The body is strict (no unknown fields; real booleans only).
  - At most 8 windows, each at most 11 characters.
  - The zone must match `^[A-Za-z][A-Za-z0-9_+/-]{0,63}$` (no dots, so no path traversal) and be a known `zoneinfo` key.
  - Windows are checked by `qw_domain.notifications.Preferences`: malformed, empty or whole-day windows are 400 with a field pointer.
  - `redact_financial_values: false` is 422 `detail_exposure_unsupported`.
  - Stored preferences that fail verification give 409 `integrity`, and nothing is written.
- **Feed.** With `in_app` off, the in-app row is dropped in SQL (so keyset pages stay exact), except for the safety category `risk_pause`. External rows stay listed: they are delivery records. If the preferences fail verification, the feed acts as if `in_app` were off and adds `unavailable:notification_preferences/integrity` to coverage. It never shows more than the user allowed.
  - Quiet hours and redaction do not change the feed; they govern external sends.
  - The record's stored `listed` still applies. A record produced while `in_app` was off stays unlisted after `in_app` is turned back on. No producer exists yet.
- **Store pattern** (as pause_store and feedback_store):
  - forced RLS; qw_app has SELECT and column INSERT; qw_worker has nothing yet;
  - append-only for the owner too;
  - `recorded_at` is the DB clock (at most 60 s back, never ahead) and never before the previous revision;
  - each revision is revision + 1 and names the previous hash, and its session is the user's own live session.
  
  The lock is `notification_preference:<tenant>:<user>`, shared to load. It is taken after `risk_pause:<tenant>`, and listNotifications takes them in that order. On load the store re-hashes every revision and checks revision numbering, the chain, time order, and that email and push are off. It then builds the domain `Preferences`, and any failure is `integrity`.
- An audit event `notification.preferences_set` is written for every change.
