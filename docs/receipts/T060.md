## Ledger INSERT trade-off (review round 1, finding 1; accepted)
Whoever holds the qw_migrate credential can insert the ledger row of the **next** pending migration, so the runner skips it. The reviewer reproduced this, and `test_qw_migrate_can_forge_only_the_next_ledger_row` pins it: a forged 0002 makes the next run start at 0003, which then fails without 0002's tables. It is accepted because it adds no capability: that login owns every app object and can already undo any migration with DDL (drop a policy, revoke a grant, drop a table). The guard narrows it: a row that leaves a gap is refused at commit, and that login cannot update or delete rows, disable or drop the trigger, drop the function, or set `session_replication_role` (each tested; `InsufficientPrivilege`). Protecting the qw_migrate credential remains the control (decision 107).

## Negative/adverse cases (all SYNTHETIC)
- Inline secrets: `QW_SECRET_KEY`, `QW_NOTIFICATION_KEYS`, `PGPASSWORD`, `PGSERVICE`, `PGSERVICEFILE` set (including empty) are refused with `InlineSecretError`; the canary value appears in neither `str` nor `repr` of the error, nor in `qw-api`'s or `qw-migrate`'s output.
- Files: group/other bits (0640, 0604, 0620, 0610, 0601, 0644), unset variable, relative path, missing file, a directory, a FIFO (opened without blocking), empty, 16385 bytes, a file owned by another uid (euid patched), whitespace or non-ASCII keys, and a key under 32 bytes are refused. 16384 bytes is accepted.
- Connection strings: `password=...`, `password=`, `sslpassword=`, a URL password, a URL `?password=`, `service=`, no `passfile=`, a 0644 passfile, an unparsable string and `servicefile=` (unknown to this libpq, refused as unparsable) are refused, before any connection.
- Keyring file: not JSON, not an object, a key that is not a string, and a seal key equal to `secret_key` are refused without echoing the content.
- Passfile path: a symlink, a missing path, and a file in a 0770, 0707 or 1777 directory are refused; a 0755 directory is accepted. A `*_FILE` key (read once, at start) may still be a symlink to a private file. `/proc/self/environ` is refused for both (size 0).
- `qw-api` refuses, before serving and with exit 2, a superuser database login and an unreachable database (output exactly `refused: database unavailable (OperationalError)`). `qw-migrate` refuses an uninitialised database (no ledger is created); a ledger whose INSERT grant was revoked or whose guard was removed (the `LedgerUnguarded` message); a ledger without the 0001 row (the generic message); a superuser login; a login granted a superuser role, with `INHERIT TRUE, SET FALSE` and with `INHERIT FALSE, SET TRUE`; and a qw_app (non-qw_migrate) login. In each case nothing more is applied.
- Ledger guard: a qw_migrate insert of version 5 over `{1}` fails at commit (`IntegrityConstraintViolation`). An old-runner ledger (trigger and function dropped, grants revoked) is refused by `qw-migrate` and repaired by one superuser `migrate()`, which logs once (a second run is silent). A disabled trigger is re-enabled the same way. `qw-migrate` then succeeds.
- The reviewer's `r21_p2.py` libpq probe, re-run: still accepted are a duplicated `passfile=` (libpq uses the last, which is the one checked), `options='-c password=x'` (a server setting, not a credential), `sslkey=` (a path) and multi-host strings; `PGPASSFILE` is not refused because `passfile=` overrides it.
- Defect found by the tests and fixed: `has_table_privilege(role, table, 'SELECT, INSERT')` is true when *either* privilege is held, so the first preflight passed a ledger with INSERT revoked and the migration failed later; it now requires each privilege.
- Password authentication: the throwaway harness cluster and CI's service both use trust auth, so there the passfile is checked but not what authenticates. The touched DB tests were also run against a separate local PostgreSQL 16.15 cluster whose `pg_hba` requires `scram-sha-256` for every TCP connection (confirmed with `pg_hba_file_rules`, and a connection without a password fails with `fe_sendauth: no password supplied`). There the qw_migrate and qw_app logins authenticated only through their generated passfiles.
