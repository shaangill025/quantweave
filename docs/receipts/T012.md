## PR A — postings and event constructors

### Changes
- `packages/domain/src/qw_domain/postings.py` (new)
  - `SourceObservation`: account, `SourceRef`, `observed_at`, `effective_at`, a read-only string payload and a SHA-256 fingerprint over account, source, record, effective time and payload. Receipt time is excluded.
  - `MoneyPosting` (`BookAccount`, `Money`, optional instrument sub-ledger) and `UnitPosting` (`UnitAccount`, `InstrumentId`, `Quantity`) on one `JournalEvent` (C-12).
    - Each set is empty or has at least 2 lines, and at least one set is non-empty. Zero lines are rejected.
    - Money balances per currency (F-01). Units balance per instrument against `unit_clearing` or `corporate_action_clearing` (F-02).
    - Only `Money` and `Quantity` are accepted, so scale violations are rejected, never rounded.
  - `event_id` fingerprints source identity plus economic content. The idempotency key is tagged: `("record", account, source, record)` or `("reversal", account, original_id)`. No source id can forge a reversal key.
  - Constructors (spec §4 "Supported economic events"): `deposit`, `withdrawal`, `fee`, `interest`, `dividend` (cash payment), `buy`, `sell`, and `split` (forward and reverse).
    - Cost convention, spec §5 "Cost and P&L reference convention" and spec §4 "Monetary and unit ledgers" (F-03): acquisition fees capitalise into cost; disposition fees reduce proceeds.
    - A partial sale takes proportional cost. Spec §5 names no lot-selection method, so this is average cost, `economic_average_cost/1`. The remaining cost is rounded up at scale 12 using exact `Fraction` arithmetic, and allocated = cost − remaining.
    - The raw fee is kept on the event.
  - `Holding` carries account and instrument. `sell` and `split` reject a holding for another account or instrument (`holding_mismatch`). `sell` also rejects `short_sale_unsupported` and `cost_unknown`. `split` rejects `split_not_long` and `split_fraction` (quarantine, e.g. 100 × 1:3).
  - **Limitation:** the constructors trust the `Holding` snapshot they are given; PR B's `Journal.sell`/`Journal.split` derive it from the journal.
- `packages/domain/tests/test_postings.py` (new, 26 tests, SYNTHETIC)
  - NUM01 postings and NUM02 split postings, with values read from `numerical_oracles.json`.
  - Rounding: cost 100 over 3 units, sold 1, 1, 1, checked against an exact `Fraction` ceil oracle. Remaining is 66.666666666667, then 33.333333333334, then exactly 0, and allocated + remaining = cost at each step.
  - 18 rejection cases.
  - Type and scale rejections.
  - Cash-only events and the reverse split.
  - Fingerprints and the forged reversal key.
  - Properties: every generated event, and any list of them, balances per commodity; a split preserves qty × price exactly with no money postings.

## PR B — journal store, corrections and positions

### Changes
- `packages/domain/src/qw_domain/journal.py` (replaces the single-module version)
  - `ObservationLog`: same record and fingerprint is a duplicate. Same record with other content is a conflict, and the original is kept.
  - `Journal.post`: the same key with the same event is a no-op; the same key with another event is a conflict and is not posted. `recorded_at` is non-decreasing. A `SELL` that would leave a negative position at its effective time is refused, so a double sale from a stale snapshot cannot post.
  - `Journal.correct` is atomic. The reversal (sourced to the correction record) and the replacement are both validated before either is appended. A `link_unknown` error (e.g. a replacement for another account) or a `CONFLICT` (e.g. the replacement's source key is taken) appends nothing.
  - `Journal.sell` and `Journal.split` derive the holding from the journal as of the event's effective time. They ignore an event already held under the same source record, so a re-import is a duplicate, not a conflict. A raw split event passed to `post` still trusts its caller's snapshot.
  - `reverse`, `reversal_of(id, known_as_of)`, and `entries`/`events(known_as_of)` let any earlier knowledge state be replayed (F-05).
  - `materialize`: a pure fold over postings giving holdings (quantity and cost), cash per account and currency, and realised P&L.
    - A negative quantity is kept and flagged `unsupported_short`.
    - A net-zero or never-posted cost is `None` (unknown), never 0.
    - **Dividends and interest (income) and fees (expense) move cash but are not totalled into income or expense figures.**
- `packages/domain/tests/test_journal.py` (rewritten, 11 tests, SYNTHETIC)
  - NUM01 and NUM02 from `canonical_transactions.csv` through `Journal.sell`/`Journal.split`, with values read from the oracle file.
  - CSV re-import gives duplicates; a changed row is a conflict.
  - A stale double sale is refused, both raw and through the helper.
  - Accounts stay distinct.
  - A correction is checked at two knowledge times.
  - Atomicity negatives: another account gives `link_unknown`, and a taken source key gives `CONFLICT`. In both cases the entries are unchanged and the original is not reversed.
  - A deposit from source `reversal` cannot block a reversal.
  - Properties (derandomized, 200 examples):
    - Each event's position change equals its effect in an independent exact model of the inputs. This is exact for cash and units; a sale's cost and realised P&L are within 1e-12.
    - Reversing any event undoes exactly that modelled effect, keeps the original, and has the original's effective time.
    - Re-posting gives identical positions, and the whole journal balances.
    - Average cost is checked against an exact `Fraction` model with nonzero sell fees and arbitrary sell fractions. Remaining cost is never below the model and never more than 1e-12 per sale above it. Remaining cost minus realised P&L is exact. Selling to zero leaves cost exactly 0 and realised P&L exact.
