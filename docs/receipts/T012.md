## PR A — postings and event constructors

### Changes
- `packages/domain/src/qw_domain/postings.py` (new)
  - `SourceObservation`: account, `SourceRef`, `observed_at`, `effective_at`, a read-only string payload and a SHA-256 fingerprint over account, source, record, effective time and payload. Receipt time is excluded.
  - `MoneyPosting` (`BookAccount`, `Money`, optional instrument sub-ledger) and `UnitPosting` (`UnitAccount`, `InstrumentId`, `Quantity`) on one `JournalEvent` (C-12).
    - Each set is empty or has at least 2 lines, and at least one set is non-empty. Zero lines are rejected.
    - Money balances per currency (F-01). Units balance per instrument against `unit_clearing` or `corporate_action_clearing` (F-02).
    - Only `Money` and `Quantity` are accepted, so scale violations are rejected, never rounded.
  - `event_id` fingerprints source identity plus economic content. The idempotency key is tagged: `("record", account, source, record)` or `("reversal", account, original_id)`. No source id can forge a reversal key.
  - Constructors (spec §4 "Supported economic events"): `deposit`, `withdrawal`, `fee`, `interest`, `dividend` (cash payment), `buy`, `sell`, and `split` (forward and reverse).
    - Cost convention, spec §5 "Cost and P&L reference convention" and spec §4 "Monetary and unit ledgers" (F-03): acquisition fees capitalise into cost; disposition fees reduce proceeds.
    - A partial sale takes proportional cost. Spec §5 names no lot-selection method, so this is average cost, `economic_average_cost/1`. The remaining cost is rounded up at scale 12 using exact `Fraction` arithmetic, and allocated = cost − remaining.
    - The raw fee is kept on the event.
  - `Holding` carries account and instrument. `sell` and `split` reject a holding for another account or instrument (`holding_mismatch`). `sell` also rejects `short_sale_unsupported` and `cost_unknown`. `split` rejects `split_not_long` and `split_fraction` (quarantine, e.g. 100 × 1:3).
  - **Limitation:** the constructors trust the `Holding` snapshot they are given; PR B's `Journal.sell`/`Journal.split` derive it from the journal.
- `packages/domain/tests/test_postings.py` (new, 26 tests, SYNTHETIC)
  - NUM01 postings and NUM02 split postings, with values read from `numerical_oracles.json`.
  - Rounding: cost 100 over 3 units, sold 1, 1, 1, checked against an exact `Fraction` ceil oracle. Remaining is 66.666666666667, then 33.333333333334, then exactly 0, and allocated + remaining = cost at each step.
  - 18 rejection cases.
  - Type and scale rejections.
  - Cash-only events and the reverse split.
  - Fingerprints and the forged reversal key.
  - Properties: every generated event, and any list of them, balances per commodity; a split preserves qty × price exactly with no money postings.

## PR B — journal store, corrections and positions

### Changes
- `packages/domain/src/qw_domain/journal.py` (replaces the single-module version)
  - `ObservationLog`: same record and fingerprint is a duplicate. Same record with other content is a conflict, and the original is kept.
  - `Journal.post`: the same key with the same event is a no-op; the same key with another event is a conflict and is not posted. `recorded_at` is non-decreasing. A `SELL` that would leave a negative position at its effective time is refused, so a double sale from a stale snapshot cannot post.
  - `Journal.correct` is atomic. The reversal (sourced to the correction record) and the replacement are both validated before either is appended. A `link_unknown` error (e.g. a replacement for another account) or a `CONFLICT` (e.g. the replacement's source key is taken) appends nothing.
  - `Journal.sell` and `Journal.split` derive the holding from the journal as of the event's effective time. They ignore an event already held under the same source record, so a re-import is a duplicate, not a conflict. A raw split event passed to `post` still trusts its caller's snapshot.
  - `reverse`, `reversal_of(id, known_as_of)`, and `entries`/`events(known_as_of)` let any earlier knowledge state be replayed (F-05).
  - `materialize`: a pure fold over postings giving holdings (quantity and cost), cash per account and currency, and realised P&L.
    - A negative quantity is kept and flagged `unsupported_short`.
    - A net-zero or never-posted cost is `None` (unknown), never 0.
    - **Dividends and interest (income) and fees (expense) move cash but are not totalled into income or expense figures.**
- `packages/domain/tests/test_journal.py` (rewritten, 11 tests, SYNTHETIC)
  - NUM01 and NUM02 from `canonical_transactions.csv` through `Journal.sell`/`Journal.split`, with values read from the oracle file.
  - CSV re-import gives duplicates; a changed row is a conflict.
  - A stale double sale is refused, both raw and through the helper.
  - Accounts stay distinct.
  - A correction is checked at two knowledge times.
  - Atomicity negatives: another account gives `link_unknown`, and a taken source key gives `CONFLICT`. In both cases the entries are unchanged and the original is not reversed.
  - A deposit from source `reversal` cannot block a reversal.
  - Properties (derandomized, 200 examples):
    - Each event's position change equals its effect in an independent exact model of the inputs. This is exact for cash and units; a sale's cost and realised P&L are within 1e-12.
    - Reversing any event undoes exactly that modelled effect, keeps the original, and has the original's effective time.
    - Re-posting gives identical positions, and the whole journal balances.
    - Average cost is checked against an exact `Fraction` model with nonzero sell fees and arbitrary sell fractions. Remaining cost is never below the model and never more than 1e-12 per sale above it. Remaining cost minus realised P&L is exact. Selling to zero leaves cost exactly 0 and realised P&L exact.
- `docs/receipts/T012.md`: this section.

## Increment 2 — PostgreSQL persistence

Worktree `/home/user/quantweave`, branch `t012-journal-persistence`, base `7ebcdfc`. No new dependencies, no network. The worker did not commit. This revision answers the cross-model review (CHANGES REQUESTED, items 1–7).

### Changes
- `sql/0007_journal.sql` (new; forward-only, owner `qw_migrate`).
  - Tables: `source_record`, `ledger_event` (header), `posting` (money) and `unit_posting` (units), linked by event id (C-12).
  - All have FORCED RLS on `app.tenant_id` and composite tenant FKs. The `reverses`/`supersedes` FKs include the account.
  - Enums mirror the domain. There is no status column (C-13).
  - Grants:
    - `qw_app` and `qw_worker`: SELECT and column INSERT on all four tables.
    - `qw_ingest` (T008 §5): SELECT and INSERT on `source_record` only, plus EXECUTE on `app.current_tenant_id()`.
    - No UPDATE, DELETE, TRUNCATE or PUBLIC.
  - **Append-only:** statement triggers refuse any role's ordinary UPDATE, DELETE and TRUNCATE. The owner and a superuser can still disable triggers or use replica mode, so those credentials stay out of runtime and need audit.
  - **Revision and knowledge time:** a BEFORE INSERT trigger takes the per-account advisory lock (held to commit, on every path including raw INSERT). It then sets:
    - `account_rev = latest + 1`: gapless, visible in assignment order, UNIQUE per account;
    - `recorded_at = greatest(clock_timestamp(), latest)`;
    - `tx_id`.
    - None of these is insertable, and owner-supplied values are overwritten.
    - **Only `account_rev` is a stable as-of key.** `recorded_at` is informational: an "as known at t" read can later gain an event stamped ≤ t.
  - Lines may be added only in their event's transaction (`tx_id`).
  - **Deferred constraint trigger `balanced`** checks at commit:
    - each posting set has 0 or ≥ 2 lines, and at least one set is non-empty;
    - money is balanced per currency and units per instrument;
    - a reversal is the exact negation of its original (EXCEPT ALL plus line counts, same effective time), and never of a reversal;
    - a superseding event comes after its original's reversal.
  - Generated `idempotency_key` is UNIQUE per account.
  - **Decimals:** clients insert a canonical string `wire` whose CHECK is the MoneyAmount/Quantity class. `numeric(38,12)` is generated from it, so scale 13 is an error, not a rounding. Timestamps are `timestamptz`.
  - There are no SECURITY DEFINER functions.
- `journal_store.py` (new)
  - `post` and `correct`: lock the account, replay it into a domain `Journal` in `account_rev` order, validate the new event with the domain rules, then insert. A repeat gives DUPLICATE; another event under a held key raises `JournalConflict`.
  - `observe` stores source records.
  - `load_journal(tx, account, known_as_of, as_of_rev)` recomputes every event id and raises `JournalIntegrityError` on a mismatch.
  - `revision()` returns 1 + the latest `account_rev`. This equals the loaded `Journal.revision`, which is what T014 N3 needs.
  - Docstring notes:
    - lock several accounts in sorted order, or opposite orders can deadlock;
    - each write replays the whole account, so n events in one transaction cost O(n²) (T014).
- `tests/test_journal_store.py` (new, 27 DB tests, SYNTHETIC). They run as non-superuser runtime roles unless a test says the superuser plays the owner.
- `tests/test_tenancy.py`: the 4 tables are added to the forced-RLS list.

### Scenarios covered (tests)
- **Round trip:**
  - NUM01 + NUM02 from `numerical_oracles.json`: the loaded events and `materialize` equal the domain (cash 738, realised 38.60, 12 units, cost 300.60 = 25.05 × 12);
  - Hypothesis journals (12 derandomized examples) round-trip as `qw_worker`.
- **Direct INSERT is refused at commit:** unbalanced money or units, a single money or unit line, no lines, scale 13, non-canonical `1.50`, zero, and lines added to a committed event.
- **Links below the adapter:**
  - refused: a supersede with no reversal, a wrong amount, a line-count mismatch, another effective time, a non-negated reversal of a split's units, a reversal of a reversal;
  - a cross-account `reverses` fails the FK; a second reversal fails the unique key;
  - accepted: the unit-only reversal of a split.
- **Revisions:**
  - a transaction started before another's post, posting afterwards, leaves an `as_of_rev` read unchanged (the reviewer's interleaving);
  - a raw INSERT whose transaction started first, but which waited on the lock, replays after the holder's two events (commit order);
  - a rolled-back insert leaves revisions gapless: [1, 2, 3, 4].
- **Append-only, grants and RLS:**
  - UPDATE, DELETE and TRUNCATE: privilege error for the runtime role, trigger error for the superuser's ordinary DML;
  - `recorded_at`/`account_rev` cannot be inserted, and owner values are overwritten;
  - RLS isolates tenants;
  - `qw_ingest` can write a source record but cannot read `ledger_event`, `posting` or `unit_posting`.
- **Idempotency and concurrency:**
  - DUPLICATE, `JournalConflict`, and a raw duplicate key gives UniqueViolation;
  - the short-sale guard applies through the store;
  - two concurrent posts give one row.
- **Correction:** 3 events, positions equal the domain (cost 491). An as-of read at revision 2, or at the original's `recorded_at`, returns only the original.
- **Integrity and catalogue:**
  - a balanced row with a forged id raises `JournalIntegrityError` on load;
  - the trigger functions are invoker-rights with `search_path=pg_catalog`, `balanced` is deferred, and no app role holds UPDATE, DELETE or TRUNCATE.

### Open gates, threats and limitations
- **Threat, open:** a balanced row with a forged id, or one that breaks a domain rule, written by a trusted runtime role (`qw_app`/`qw_worker` is trusted code) permanently blocks loading that account. There is no quarantine or recovery design yet.
- Owner and superuser credentials can bypass the append-only triggers (see above).
- Each write replays the whole account.
- No FK from events to `source_record`, and accounts are text ids with no FK.
