`ReceiptProposer` is a real `SelfProposer`. It reads only the receipt's executed policy, proposals and selection; it ignores ids, times, costs and fixtures. Rules:
- **R1:** append missing operators, in enum order.
- **R2:** put the selected proposal's operator first; if nothing improved, put the tried operators last.
- **R3:** raise a spent budget to every move the operators can make (at most 8).
- **R4:** switch `first_improving` to `best_of_budget` when the cycle stopped with moves and budget left.

Refusals: a result with V0's behaviour raises `no_change`. A receipt that is not of the current policy, or names a pick it never proposed, raises `receipt_mismatch`. The output is the three knobs only and still passes through `from_payload`, `identical_relabel` and the recording of the source cycle and its output hash.

Recursion: from V0's receipt it derives V1 = budget 3, (date, value), first_improving. From V1's receipt it derives V2 = `best_of_budget`, and V2 is a fixed point (`no_change`). An exhaustive test over 192 policy and base receipts finds no relabel and no output beyond the three knobs.

`measure` is the assessor's side. Each policy runs its cycle (the search) from the source cycle's research base on the development fixture that the source cycle ran on. The config each search selects is then scored on the protected, plan-bound promotion fixture. `promotion_gain` is therefore an out-of-sample difference. The two slots cannot be swapped: the development slot refuses a non-development fixture (`not_development`) and one the source cycle did not run on (`source_fixture`); the scoring slot refuses a non-promotion fixture (`not_promotion`).

Other refusals:
- `self_certification` (optimizer identities, including V1's version) and `assessor_not_registered`;
- `test_access_changed`, `answer_key_changed` and `evidence_class`;
- `baseline_hash`, `not_from_baseline` (the candidate's parent is not V0's version), `source_cycle`, `base_mismatch` and `candidate_experiment`;
- `cost_exceeds_limits`.

Metrics: `promotion_gain`, `replayed_output`, `payload_invalid`, `identical_relabels`, `threshold_changes` and `cost_usd` (Decimal; V1's declared worst-case cycle cost). A payload that is unparsable, does not match the artifact hash or has stray keys is measured as V0, so it fails closed.

`scorecard(id, max_cost, limits)`. - This section.

**Cycle receipt wire.** `CycleReceipt.wire()` gives JSON values only: decimal strings, UTC `Z` instants, the executed policy and a `receipt_hash`. `from_wire` is its exact inverse. It refuses:
- unknown or missing keys (`wire_keys`);
- wrong JSON types, including floats and booleans (`wire_type`);
- naive, non-UTC or non-canonical times (`wire_instant`);
- non-canonical or exponent amounts (`wire_decimal`);
- malformed hashes (`wire_hash`);
- unknown proposal knobs and values and malformed authorities (`wire_value`);
- a malformed executed policy, such as `proposal_budget` `"01"` or `"9"`, or `selection` `"zzz"`: `OptimizerConfig.from_payload` refuses it as `value` (a non-string knob is `wire_type`);
- a runner that is not the executed policy (`runner_config_mismatch`, also refused by `wire()`);
- a changed `outputs_hash` or `receipt_hash` (`hash_mismatch`).

**Lineage: unverified data and the sealed receipt.** `UnverifiedLineage` records the spec's recursive-lineage fields:
- `optimizer_v0_hash` (with V0's cycle receipt);
- `candidate_v1_hash` and its non-empty `diff`;
- `assessor_manifest_hash`: the frozen protocol's content hash, covering the assessor, scorecard and test access, which the signed release manifest also binds;
- the signed approval: release id, approving principal, the maintainer's step-up receipt id and the signature reference;
- the install operator, `install_self_approved` (decision 23, as T051 `Install` records it) and `installed_v1_hash`;
- `next_cycle`: V1's cycle receipt, run under `release:<release id>`;
- the next candidate's lineage (required);
- the verdict's limitations and `LIMITATIONS`.

It has a strict wire with a `lineage_hash`. `from_wire` returns an `UnverifiedLineage`; it also refuses an empty `verdict_limitations` (`wire_value`), so a gate-lifted or synthetic mark cannot simply be dropped.

`LineageReceipt` is a separate, read-only type holding one. Only `lineage()` and `verify_lineage()` make one; the constructor refuses anything without the module's private seal (`lineage_unverified`).
- `lineage()` derives every field from the registry, the deployment and the cycles, only once `verify_recursion` finds nothing. Otherwise it raises `lineage_unverified` with that function's reasons, so those checks are reused rather than copied.
- `verify_lineage(unverified, registry, deployment, base, dev, next_candidate)` re-runs exactly that derivation, so `verify_recursion` re-runs and the release, approval, step-up receipt, signature reference, install and verdict limitations are read again from the deployment and the verdict. Any field that differs is refused as `lineage_mismatch: <fields>`.
- `next_cycle_run_id` and `experiments.wire` accept only a `LineageReceipt`. mypy enforces this (the tests' `type: ignore[arg-type]` lines would be unused otherwise), and at run time anything else is a `TypeError`.
- Tests: a genuine wire round-trips through `verify_lineage` to an equal receipt. Six forgeries, each locally consistent and re-hashed, parse but cannot be served and are refused by `verify_lineage`: approval step-up, signature reference, install operator, verdict limitations, a release id with a matching next-cycle authority, and a fabricated next cycle with matching candidate lineage.

Construction of an `UnverifiedLineage`, and therefore `from_wire` even after a forged re-hash, raises `lineage_refused` for:
- `self_certification`: an assessor sharing an actor, route or family with V0, or carrying V0's or V1's version (`_is_optimizer`);
- `self_approval`: an approver who is the producer (V0's actor) or the assessor; `self_install`: an operator who is the producer;
- `self_approved_mismatch`: approver and operator are the same principal exactly when the install is recorded self-approved;
- `next_runner_not_v1`: the runner hash, executed policy or authority is not the installed V1's release, or the next cycle ran before V0's;
- `lineage_break`;
- `identical_relabel`, `diff_mismatch` and `next_lineage`;
- `lineage_incomplete`: no next candidate, or a V1 cycle that selected nothing. The spec lists the next candidate's lineage as a required field. `lineage()` raises this code before `lineage_unverified`, with any reasons `verify_recursion` found (for example a V0 replay, which selects nothing, gives `lineage_incomplete: replayed_output`).

**Separation of duties: which rule applies.** The lineage enforces exactly what T051 and decision 23 require, through one helper, `_duties`, now shared with increment 1's runner gate (`_assessment`):
- **T051 `prepare_release`:** the approver is neither the producer nor the assessor (`self_approval`). Here, as in the runner gate, the comparison is case-insensitive.
- **The runner gate (increment 1):** the producer does not install (`self_install`).
- **Decision 23, as T051 `DeploymentLedger` enforces it:** approver and operator may be one person only under the deployment's explicit solo-maintainer opt-in, and such an install is recorded `self_approved`. The deployment refuses it without the opt-in (`separation_of_duties`) and refuses a wrong flag (`self_approved_mismatch`). The lineage carries the flag and checks it against the identities; `verify_lineage` re-reads it from the install.
- The earlier extra refusals of approvers or operators named after an optimizer version are removed, because neither T051 nor the decisions have that rule. The assessor's version check stays in `self_certification`.
- T051 and the decisions do not contradict each other.

A mismatch raises `lineage_binding`, which the API `wire(rec, lineage=None)` maps to 409 `integrity`, the module's convention for records that fail checks (tested). Without a lineage it returns null and never invents a value.
