### Rules
- **Three separate acts (R099, AT034).** The maintainer signs a manifest, the operator installs it, and the tenant adopts it (through T027 `StrategyRegistry.adopt` with step-up consent). Each act needs its own step-up receipt: install, rollback and pause check the ledger's step-ups and every adoption step-up in the strategy registry they are given; adoption checks the ledger's and earlier adoptions'. Reuse is `step_up_reused`. Install never writes an adoption. A tenant's `strategy_state` keeps the version it adopted, with that adoption's receipt hash, after a newer release is signed and installed. Proposals bind to that version and hash.
- **Releasable candidates (R030, R039, R076).** Three conditions apply:
  - The candidate's latest recorded T044 verdict must be accept-for-review. A later reject supersedes an earlier accept.
  - The protocol must be installation-scoped (`tenant_scope`) and must require `maintainer_release`. The personal-adaptation path therefore needs a different authority (deferred).
  - The target must not be code or optimizer (`sandbox_unqualified` until T007).

  The producer or assessor actor cannot approve (`self_approval`), and approval cannot come before the verdict. For a strategy release, the strategy manifest's `implementation_hash` must equal the candidate's artifact hash.
- **Manifest and signature (R092).** The canonical manifest covers release and component (`<target>:<id>`), candidate, artifact and protocol hashes, verdict id, the frozen protocol's required approval classes, schema compatibility (`min`, `max`, `writes`), strategy version and material hash, rollback version (the protocol baseline) and the maintainer's principal, step-up and time. `verify_release` checks the key id against the operator's trusted set, algorithm, key principal = approver, validity at approval, revocation at use, the recomputed manifest hash and the signature. A key marked `test_only` (the default) is refused unless the deployment allows test keys; a non-test key must use an algorithm in `PRODUCTION_ALGORITHMS`, which is empty until T009 (`algorithm_not_production`). A raising verifier reads as `bad_signature`.
- **Signature primitive.** The stdlib has no asymmetric signature and T009 has approved no crypto dependency. `Signer`/`Verifier` are protocols, and the only implementation is a test-only HMAC signer in the test file. HMAC is symmetric, so production needs an asymmetric scheme such as Ed25519 from a reviewed dependency. Operators then hold public keys only (R096). This is an open gate, not a pass.
- **Install (operator).** The operator must be listed for the deployment (AT039: a tenant user cannot deploy) and must not be the release's approving maintainer (`separation_of_duties`, an orchestrator decision the owner may overrule). Events are appended in time order. The release must verify, and the deployment's state schema must be inside its range. State schema only moves forward (`max(current, writes)`). Re-installing a release id is `release_conflict`.
- **Rollback.** Rollback appends a `Rollback` event. It withdraws the component head in favour of the most recent earlier install that is not withdrawn, not paused, verifies now, and runs on the current schema. If no such install exists (`no_prior_release`, `schema_incompatible:N`, `key_not_valid`, ...), a `Pause` with the per-candidate reasons is appended instead. The head stays as it was but suspended. The schema is never downgraded and no earlier event changes (tests compare the entry prefix). Tenants on a withdrawn or paused release read `paused` with those reasons. They are never moved to another version, even one they adopted before: they re-adopt explicitly. An explicit `to_release_id` that cannot run is refused (`rollback_target`); only the automatic search pauses. `strategy_state` refuses read times before the ledger's last event. Construction replays all events and refuses forged or reordered histories; the trusted key map is read-only.
- **Authority scope mapping (T044 `ApprovalClass` → schema).**
  - `maintainer_release` → `hosted_maintainer`.
  - `operator_install` → `self_hosted_operator` on self-hosted, or `hosted_maintainer` on hosted.
  - `user_strategy_adoption` → `user_strategy_adoption`.

  The `change_kind` mapping is: strategy → `strategy`, application_code → `application`, recursive_optimizer → `optimizer`, and the others → `configuration`. Both mappings are interpretations for owner review.

## Negative cases (SYNTHETIC)
- **Release refused:** no verdict; a later reject; tenant-scoped protocol; producer or assessor approving; approval before the verdict; a missing or mismatched strategy manifest; code and optimizer targets with forged accept verdicts; personal adaptation; an invalid compatibility range.
- **Verification fails:** an untrusted key; the same key id with a forged secret; a tampered compatibility, approver or approval list; the wrong key principal; a revoked key; a key valid only after the approval; a test key in a production deployment.
- **Install refused:** a non-operator; a reused maintainer step-up; installing before approval; a test key not allowed; schema incompatible; a duplicate release.
- **Adoption refused:** a tenant outside the deployment; a release not installed; a reused operator, maintainer or earlier adoption step-up; adoption before install; a mismatched strategy material hash; a withdrawn release.
- **Rollback and replay:** a target that is unknown or in another component; forged ledger replays (bad signature, reordering, step-up reuse, rollback from a non-head, pause on a non-head, non-operator).

## Acceptance scenarios applied (SYNTHETIC; not release proof)
- **AT034, AT099:** maintainer signature and install do not change a tenant's adopted version. The three typed approvals are separate acts with their own step-ups.
- **AT030, AT092:** no self-approval. Tampering with the approval list, compatibility range or approver fails verification. A forged key fails.
- **AT039:** tenant-scope candidates cannot be released and non-operators cannot install.
- **AT076, partial:** the release and rollback mechanism exists. Code and optimizer stay blocked on T007.
- **Not addressed here:** AT051 (hosted/self-hosted migration), AT087 (archive import) and AT096 (operator-held asymmetric keys, install without vendor bootstrap). These belong to later increments.

## Unresolved gates and deferrals
- **Signature scheme:** a production asymmetric signature needs a T009-reviewed dependency. Until then only test HMAC keys exist.
- **Personal adaptation:** a tenant-scope release path (operator install plus user adoption without a maintainer signature) is not built.
- **Automatic rollback:** rollback under an already-approved operational policy is not built. Rollback here is operator-initiated with step-up.
- **Recursion:** the T044 schema fields `next_cycle_run_id` and `release_receipt_id`, and V1 running the next cycle, are not built.
- **Not yet built:** persistence, routes (`AdoptVersion`, install and rollback endpoints) and server clock. Approver, operator, step-up and times are caller-asserted. Step-up receipts are not verified against T010 records. Maintainer step-up reuse is detected only per deployment.
- **Trusted verdicts:** verdicts are trusted as recorded (T044 N3). A forged accept verdict recorded through `record_verdict` would be releasable for non-sandboxed targets. Persistence must store only `assess` output.
- **Not yet built:** post-promotion regression tracking, invalidating dependent recommendations, and migration/backup procedures for irreversible schema changes.
- **Other tasks:** AT051, AT087 and AT096 belong to the portability, archive and self-hosted install tasks.

- **Red phase observed.** The two new tests failed before the fix (2 failed). A scratch script installed a hand-built `application_code` and a `recursive_optimizer` manifest into a SYNTHETIC deployment: both became the head and `verify_release` returned `[]`.
- **One gate source.** `_target_gates(target, approvals)` reads `SANDBOX_TARGETS` (from `improvement`, the same constant `assess` uses) and the `maintainer_release` approval. `prepare_release` raises its first result. `manifest_refusals(manifest)` adds the manifest-only invariants. `verify_release` puts those reasons first in every result, including `untrusted_key`. So install, ledger replay, rollback targets, `runnable`, `strategy_state` and `adopt_release` are all covered. `install` raises a typed `ReleaseError` with the first reason as its code (for example `sandbox_unqualified`), before any check that changes state. The ledger is immutable, and the tests confirm that its entries, head, schema and step-ups are unchanged after a refusal.
- **Error precedence changed.** `install` now reports a manifest-refusal code before `release_conflict`, `step_up_reused`, `time_order` and `separation_of_duties`. Those four checks used to run first. When a manifest breaks several rules, the code is the first reason in a fixed order: target, then required approvals, then strategy binding, then component. A test with a sandbox target that also lacks `maintainer_release` pins this: the reasons are exactly `["sandbox_unqualified", "maintainer_release_not_required"]` and install raises `sandbox_unqualified`.
- **Re-checked at install (the data is in the manifest):**
  - the target is a `Target` (`target_type`), and `required_approvals` is a tuple of strings (`approvals_type`). Without the second check a bare string passed the `maintainer_release` gate through a substring `in`. A mistyped manifest is refused with that one reason, and `verify_release` stops there, because such a manifest cannot be hashed or read further;
  - target not in `SANDBOX_TARGETS` (`sandbox_unqualified`);
  - `maintainer_release` among the required approvals (`maintainer_release_not_required`);
  - strategy version and material hash present exactly when the target is `strategy` (`strategy_binding`);
  - the component is `<target>:<id>`, with a non-empty id, and the id equals the target for non-strategy releases (`component`).
- **Already re-checked before this follow-up:** the approver equals the key principal, the operator is not the approver, install does not come before the approval, and the approval is inside the key's validity window.
- **Still open: not re-checked at install (the data is not in the manifest or the ledger):**
  - approver not producer or assessor (`self_approval`): the manifest has no producer or assessor ids;
  - approval and install not before the verdict's `assessed_at`: the manifest carries only `verdict_id`;
  - installation scope (`tenant_scope`) and the latest verdict being accept-for-review: these need the T044 registry, which the ledger does not hold.

  Closing these needs the install path to take the registry, or the signed manifest to carry those fields. Both are API or wire changes left for a later increment. The second would change the manifest hash of every existing release.
