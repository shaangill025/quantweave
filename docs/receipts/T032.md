### Rules and interpretations
- **Rights**: T021 has no `research` use, so research use = `Use.RETENTION` (with the retention duration) + `Use.DERIVED_DATA` for every declared feed. Unknown, denied or unqualified -> `DatasetRefused` with every reason. A fact or membership event from an undeclared feed refuses the dataset.
- **Freeze**: records known after `as_of` are left out; `observed.end <= as_of <= freeze time`. `observed` is the declared observation range recorded in the manifest; records are not filtered to it.
- **Survivorship**: members on day D known by t = instruments whose latest known event effective on or before D is an add. A later delisting never removes a name from an earlier universe; nothing is a member before listing; a delisting known after its effective date stays invisible until known.

### Rules and interpretations
- **Evidence class**: a plan holds the dataset manifest; its hash, evidence class and observed range are read from it and cannot be redeclared. `register_plan` takes the `ResearchDataset` (whose hash is re-derived from its content on construction) and refuses unless its manifest equals the plan's in every field (`dataset_mismatch`), so a relabelled manifest with the same hash cannot be registered; `open_view` repeats the check. A plan registered through `register_plan` for a synthetic dataset therefore always yields `synthetic=True` evidence (T027 caps it). A `TrialLedger` built directly from stored entries replays them without the dataset content, so persistence must only store plans written through `register_plan`.
- **Holdout**: train/development access must lie inside its split window and may not name a holdout instrument; their views hide holdout instruments and facts not resolved to an instrument. Promotion access is protected-assessor only and refused once the plan's declared limit (default 1) is reached; refusals are recorded. Granted promotion accesses are numbered; only a completed promotion trial on access #1 yields evidence, later ones raise `holdout_reused` (additional final-test queries are not fresh evidence). Train/development trials never yield evidence.
- **Candidate binding**: every access names a `Candidate`; a trial is refused (`candidate_mismatch`) unless its family, material hash and config hash equal the candidate of the access it binds.
- **Trial count**: `trial_count(family)` = distinct trial ids in the family that were recorded (any outcome, including failed and abandoned) or saw data through a granted access, whether or not a result was recorded. `unrecorded_accesses(family)` lists the granted accesses no trial is bound to. Refused accesses saw no data and are not counted. A later multiple-testing adjustment must use `trial_count`.
- **Evidence binding**: `EvidenceRecord(ref_id=trial_id, material_hash, config_hash, tenant_id=None, synthetic, recorded_at)`, the evidence-axis shape `strategy_gate._verify` checks.

### Rules and interpretations
- **Canonical**: every `from_wire` rebuilds the record and refuses input whose `to_wire` differs, so offsets other than `Z`, `YYYYMMDD` dates, exponent or trailing-zero values, `-0`, and repeated fact versions are refused, never normalized. Floats, ints and bools are refused where a decimal string is required; `fy` must be an `int` (never `bool`) in 1900–2200; extra or missing keys are refused at every level.
- **Equal facts, equal wire**: equal decimal values (`100`, `100.00`, `1E+2`) share one wire text, so equal facts hash equally. One dataset has exactly one stored form: facts and events are kept in canonical order (above), so decision 74's `dataset_exists` can compare bytes. The digest already sorted, so the content hash, and with it the re-pinned `GOLDEN_PROTOCOL`, are unchanged by the ordering.
- **Storable datasets**: `ResearchDataset` refuses a fact whose wire does not round-trip. T023 still lets a `Fact` be built in memory with loose fields (e.g. `feed_hash="synthetic-hash"`, used by other tests), but such a fact cannot enter a research dataset.
- Not done here: decisions 73–75 (roles, `dataset_exists`, purge/revocation) are store rules.

### Plan for the store increment (coordinator decisions after review; no code here)
- **Rights terms (decision 77)**: `scope`, `jurisdiction` and `retain_for` are stored as a separate `terms` entry on the stored dataset row. They are not part of the manifest or the content hash; the row's event hash covers them, and they are re-checked at each run against the database clock.
- **Feed hashes**: the store checks that each fact's `feed_hash` is a recorded revision of its feed in the rights registry. It is not required to equal the manifest's freeze-time feed hash.
- **Facts loose in memory, strict at the dataset boundary**: accepted. T023 `Fact` keeps its in-memory looseness; `ResearchDataset` (and so the store) admits only facts whose wire round-trips.
- **L1 (low)**: `_storable` re-parses every fact on each `ResearchDataset` construction (and canonical sorting re-serializes them). That is a possible optimisation for bulk loads in the store, for example validating once at the boundary. Correctness first for now.
