## Session token scheme
`secrets.token_bytes(32)` → base64url without padding (43 characters, `[A-Za-z0-9_-]`). The stored value is `sha256(token.encode("ascii"))`, 32 bytes. Each distinct string has its own hash, so there is no non-canonical-encoding ambiguity. A malformed token is rejected before any query, and `lookup_session` returns None for it.

Lookup runs in its own transaction:
1. It clears `app.tenant_id` and sets `app.session_token_hash` to the hex digest, both transaction-local.
2. It selects sessions with `expires_at > now()` and `revoked_at IS NULL`. The hash comparison happens in PostgreSQL as a unique-index equality on a hash, so Python never compares secrets and timing does not depend on the token.
3. On exactly one row, it switches to that row's tenant context, clears the hash setting and loads the membership joined to `tenant` with `status = 'active'`. A suspended tenant's sessions therefore return None, and the check is in SQL.

It returns `SessionPrincipal(session_id, tenant_id, user_id, role, created_at, expires_at, step_up_at)`, or None when the token is unknown, expired or revoked, or the membership is gone. Expiry uses the database clock. TTL must be in (0, 30 days], checked in Python and again by the table CHECK. A shorter policy TTL belongs to the API increment. The raw token is returned once by `create_session` and cannot be recovered from the database. `qw_app` cannot read `token_hash` at all; the policy expression can, because PostgreSQL does not apply column privileges to policy quals (observed: lookup works while `SELECT token_hash` is denied).

## Trust boundary (stated plainly)
Row level security here is **defence in depth against application bugs**, such as a forgotten WHERE clause or a wrong join. It does **not** contain a compromised `qw_app` process: that role can call `set_config('app.tenant_id', <any uuid>, true)` and act inside any tenant. It can also write `step_up_at = now()` without a real step-up and choose the `actor_user_id` of an audit event. The API (and the worker for jobs) is the trust boundary for:
- deriving the tenant only from the authenticated session, never from client input;
- membership role changes, including last-owner and self-promotion guards (no role-change guard exists in the database, and `qw_app` can UPDATE `membership.role`);
- step-up: only the API may set `step_up_at`, after a real re-authentication (API-trust item);
- the audit actor field, which must be the session's user.

These are API-layer work items below, together with a separate audited support-access route (A-10).

## Unresolved gates
- Ids are globally unique primary keys (`app_user.id`, `session.id`, `audit_event.id`). If the API ever accepted a client-supplied id for an insert, a unique-violation versus success difference would be an oracle for whether an id exists in another tenant. Rule: ids are always generated by the server (as the adapter does), and the API never accepts one on create.
- CI has not run. Only the PostgreSQL 16.15 host cluster was used.
- The owner `qw_migrate` can still `ALTER TABLE … DISABLE TRIGGER` or drop policies. It is a deploy-time role only (T060/T062), and a migration doing that is visible in review, but nothing checks it automatically.
- `schema_migrations` stays in `public`.
- The global uniqueness of `app_user.id` and `session.id` does not affect isolation.
- The token policy reveals one session row to anyone who already knows its hash. Hashes are never readable by the runtime roles.

| Control | Implementation |
|---|---|
| C-03 idempotency | `app.idempotency_record`: FORCE RLS, tenant policy, composite FK, qw_app SELECT/INSERT. Requests with the same (tenant, principal, method, route, key) are serialized by a transaction-scoped advisory lock. The record stores HMAC-SHA256(`secret_key`, method, route, canonical payload) and the first 2xx response, in the same transaction as the effect. A replay returns the stored status and body with `Idempotent-Replayed: true`. Another payload gets 409 `idempotency_key_reused`. Logout and step-up put the session id into the HMAC, so reusing a key from another session also gets 409 (review fix). The key must be 16–128 characters of `[A-Za-z0-9_-]`, else 400; a missing key also gets 400. Scope: logout, step-up and role change. Login is excluded because its response carries a new session token. Step-up's HMAC leaves out the password, so a retry with the same key replays the stored `step_up_at` and makes no new change. Because of the advisory lock, a duplicate that arrives while the first request is still running waits and then gets the replay, rather than C-03's 409 `retryable`. After a successful logout the session is gone, so a later retry gets 401. |
| Throttle and lockout | `app.auth_throttle` holds HMAC keys and counters only, with no tenant data, so its RLS policy admits all rows. qw_app has only SELECT on it, plus EXECUTE on three SECURITY DEFINER functions owned by qw_migrate, each with fixed SQL and `search_path` set to pg_catalog: `throttle_hit`, `throttle_clear` (reset after success) and `throttle_purge` (deletes rows quiet for a day and not locked). A direct UPDATE, INSERT or DELETE is denied. `app.throttle_hit()` counts each attempt under a row lock. Past N attempts in the window, the key locks for base·2ⁿ, capped at `cap`. Locks are forgiven after one quiet `cap` period. Attempts are counted in their own autocommit statement, so a failed request that rolls back still counts. Keys cover account and address for both login and step-up. **The address key is hit first, and the account key is skipped while the address is locked**, so one address adds at most `max_attempts` account rows per window. The API runs `throttle_purge` at most once a minute per process. The Idempotency-Key format is checked before anything is counted. Defaults are configurable in `Settings`: 5 per account and 50 per address per 15 min, lock base 1 min, cap 1 h. While locked, the password is not checked and the response is 429 `too_many_attempts` with `retry_after_s` and `Retry-After`; this is identical for real and unknown logins. A successful login or step-up clears only the account key. A newly locked account gets an `auth.locked_out` audit event in its tenant: actor NULL for login, the user for step-up. A locked address, or an unknown login, gets a log line only, because no tenant exists for it. |
| Client address | `client_address` uses the socket peer. It reads X-Forwarded-For only when the peer is in `Settings.trusted_proxies`, and then takes the rightmost hop that is not a trusted proxy. Entries are IPs or CIDR networks, validated with `ipaddress`; hops are canonicalised. When the set is empty, `create_app` logs a startup warning. **Each deployment must configure this.** With an empty set behind a proxy, every user shares the proxy's address bucket. |
| C-02 cursors | `GET /memberships?limit=1..200 (default 50)&cursor=` is keyset-paginated by user_id. The cursor is base64url of (after-id, expiry) plus a 128-bit HMAC tag over tenant, principal, route, sort and body, valid for 1 h. Decoding is strict base64 (`validate=True`). A forged, truncated, expired, other-principal or other-tenant cursor gets 400 `invalid_cursor`. |
| Bootstrap | `qw-bootstrap --login --display-name` reads `QW_DATABASE_URL` from the environment and the password from stdin, so neither appears in argv. It connects as the runtime role and creates, in one transaction, the tenant, the owner, the argon2id credential and an `installation.bootstrapped` audit event. The singleton `app.installation_bootstrap` row (`INSERT … ON CONFLICT DO NOTHING`) refuses a second or concurrent run. There is no HTTP route. |
| Idle timeout | `session.last_used_at`. `lookup_session(…, idle)` rejects a session that has been idle longer than `idle_timeout` (default 30 min, at most `session_ttl`). It writes `last_used_at` at most every min(60 s, idle // 2). The replaced `session_update_guard` lets `last_used_at` move only forward, and only to `now()`. |

New tests (qw_app non-owner login on a migrated DB):
- **Lockout curve:** retry delays of 60, 120, 240 and 240 s, identical for an existing and an unknown login, with 4 audit events for the real one. After the lock is released, a success clears the counter.
- **Race:** 20 threads making 40 attempts get exactly 5 through.
- **Idempotency:** step-up and role-change replays are byte-identical and audited only once; another payload gets 409; a bad or missing key gets 400.
- **Cursors:** a full walk returns 5 sorted members. Forged, truncated, garbage, expired, other-principal and other-tenant cursors get 400.
- **Bootstrap:** a bad password gets 2, the first run gets 0, a second run gets 1; the owner can log in.
- **Idle:** expiry after 1 s of idleness. Backdating or pre-dating `last_used_at` is refused.
- **Proxy:** X-Forwarded-For spoofing is resisted; CIDR ranges and canonicalisation are covered.
- **Cross-session idempotency (review fix):** reusing a logout or step-up key from a new session gets 409, and the new session stays live and not stepped up.
- **Bounded rows (review fix):** 300 distinct logins sprayed from one locked address leave 4 rows. Purge removes the old unlocked rows and keeps the locked one. qw_app gets "permission denied" on a direct UPDATE, INSERT or DELETE.

Residual risks and later work:
- **Account-lockout DoS:** anyone who knows a login can keep that account locked, at most `cap` (1 h) per lock, repeatable. The address limit slows this but does not stop a distributed attacker. Possible later mitigations: per-device trust, or CAPTCHA/step-up instead of a hard lock.
- **NAT and shared addresses:** users behind one NAT, or behind an unconfigured proxy, share an address bucket (50 attempts per 15 min), so one attacker there can lock out all of them for logins.
- The request that locks an existing account does one extra query, for its audit event.
- Throttle, idempotency and bootstrap rows are never purged; there is no DELETE grant (T025).
- Login does not revoke earlier sessions.
- Credential rotation and rehash.
