### Rules (as of round 1)
- **Targets (R028, R033).** The six schema targets. `HARD_CONTROLS` turns each §11 negative control into counted-violation metrics, for example strategy: `lookahead_violations`, `survivorship_violations`, `unrecorded_trials`; optimizer: `identical_relabels`, `threshold_changes`. Code and optimizer are `SANDBOX_TARGETS`.
- **Scorecards (R029).** One per target. Each must hold every hard control as a hard `at_most 0` threshold and at least one goal threshold; dropping or loosening a hard control is `hard_control_missing`. Bounds are Decimals.
- **Frozen protocol (R084, R092).** Registered before candidates and hashed over everything it holds: target, baseline version and hash, producer, assessor, distinct-family flag, scorecard, T032 plan id and `plan_digest` (windows, embargo, holdout names, access limit, dataset and protocol hashes, approver), evidence purpose, risk policy hash, required approval classes, budget terms and the authorizing owner. Re-registering the id with any change is `protocol_frozen`, naming the fields. A budget reservation id belongs to one protocol only (`duplicate_reservation_id`).
- **Approvals (R030, R099).** `MIN_APPROVALS` is an orchestrator decision; the owner may overrule it. It follows the spec chain strictly:
  - strategy: maintainer release, operator install and user strategy adoption;
  - personal adaptation: operator install and user adoption;
  - research, evaluator, code and optimizer: maintainer release and operator install.

  The module records required classes and grants none. It has no promote, approve, install, adopt or sign function (an AST test checks this). For T051, these names must be mapped to the schema's `authority_scope` vocabulary.
- **Candidates are data.** A candidate holds an artifact hash, a string payload, runtime versions and logged T043 `Use` records. Scoring never reads the payload. Protected key names are refused, but only on a best-effort basis (N4: variants such as `x_threshold` pass, which is harmless because the payload is never read). Evidence uses must have been logged by `select` for this experiment and purpose, with development access only.
- **Lineage (R037).** The registry is append-only and replays every entry when constructed. The parent is this experiment's baseline or a candidate of the same experiment. A candidate id may not equal any protocol's baseline version. An artifact equal to the baseline's or to any candidate's in the same experiment (ancestor or sibling) is `identical_artifact`. Artifact hashes are caller-asserted (N8).
- **Scheduling (R032, R035).** Experiments are taken in queue order. Each reserves its maximum cost under `improvement` in the T037 book before work starts. A cap refusal defers that experiment and every later one (`queued_behind`): nothing is skipped or overrun. An existing reservation must carry the protocol's exact terms (category, amount, account, token limit), otherwise `reservation_terms_mismatch`. A retry keeps the original record. A closed reservation is `reservation_closed`, including a retry after the deadline once expired (N7). Missing spending authorization defers.
- **Assessor.**
  - Independence: actor and route must differ from the producer's, and the family too when configured.
  - Blocked: another assessor identity; no open reservation; a reservation with other terms; a ledger tenant or plan that differs from `plan_digest`. Only the plan digest is re-checked; the risk policy and approvals stay frozen in the protocol hash but have no external source to compare yet (N5).
  - Scores: only from the T032 ledger, and only the completed promotion trial for this candidate that the assessor's own actor ran with the assessor role. That trial's holdout read must come after both the protocol freeze and the candidate's creation (`trial_before_freeze`), with access ≤ recorded ≤ assessment time (`time_order`). It must also be the plan's first holdout read, which is plan-wide (N6: one assessed candidate per plan).
  - Insufficient evidence: a missing metric, or a negative violation count (`metric_invalid`).
  - Rejection: hard failures cannot be offset by goals. Claimed numbers must be Decimals equal to the recorded ones (`metrics_mismatch`).
  - Verdicts: accept-for-review carries no reasons; every other decision has some. Verdict ids are unique. Human promotion is always required.
- **Sandbox (T007 external gate).** Code and optimizer experiments are deferred with `sandbox_unqualified` and nothing is reserved. Their assessment is `blocked` with no scores; there is no stubbed pass.

Design decisions:
- **States.** `record` derives only proposed (no verified reservation, deferred or blocked), authorized (the frozen budget terms are reserved), and awaiting_review, rejected or failed (accept, reject, insufficient evidence). It never derives running, evaluating, approved, promoted, rolled_back or cancelled. Code and optimizer experiments are always proposed with `blocked:sandbox_unqualified` (T007). A decided record is final.
- **Only derived records are stored.** `experiment_store.record` accepts no `ExperimentRecord`: it takes the registry, ids, plan, book, outcome and assessment, and calls `improvement.record`, which runs `assess` itself. A hand-built, forged-verdict or reason-stripped record cannot be passed (tests). What this does not close: the registry, trial ledger and book are caller-supplied and not persisted, so a read cannot re-run `assess`; and a raw qw_worker INSERT with a correctly computed hash is checked only by the database rules and the domain invariants, not for provenance. Follow-up N3 is therefore narrowed (no caller-claimed verdict through the store), not closed.
- **Reasons.** Whatever the schema cannot carry is a sorted `<kind>:<detail>` reason (at most 64; kind ≤ 12 and detail ≤ 150 characters, so the served `<kind>:<id>/<detail>` is ≤ 300): `blocked:*`, `deferred:*`, `insufficient:*`, `rejected:*`, `evidence:synthetic_only`, `none:evaluation_receipt_ids`, `unavailable:parent_optimizer_version`. The list page serves them as `coverage.reasons` (partial). Over-long reasons, more than 64, or a hypothesis over 4000 characters (or with NUL) are a typed domain error, not a database error. These limits fail closed: a record whose reasons would exceed them is refused by `record` and cannot be stored (nothing is truncated). Today's sources fit: metric ids are at most 128 characters, so the longest assessor reason detail is 143 (`metric_invalid:<metric>`); a longer reason source added later (for example, an over-long metric name if that id limit were raised) would block recording.
- **Field mapping.** `protocol_id` = protocol content hash; `candidate_version`/`candidate_hash` = candidate id and artifact hash; `protected_assessor_version` = assessor version; `data_snapshot_ids` = the T032 plan's dataset id (the plan must match the frozen `plan_digest`); `evaluation_receipt_ids` = [] (no receipt store); `next_cycle_run_id` and `release_receipt_id` = null. `parent_optimizer_version`: for the recursive optimizer, the candidate's `parent_id` (the baseline only for a first-generation candidate, as in `experiment_recursive.valid.json`; a later generation names the parent candidate); for every other target it is unavailable (owner decision below). The schema does not allow null there, so such an item is withheld from `items` and named `withheld:<id>/item` plus `unavailable:<id>/parent_optimizer_version`; it is never served with a null or an unrelated value.
- **Writer.** qw_worker is the narrowest existing writer role (qw_assessor and qw_release have no login path: `check_runtime_role` admits only qw_app and qw_worker). qw_app reads only. No worker job calls `record` yet: it is used from tests and the domain service.
- **Scope.** Tenant scope only (DB CHECK `scope_id = tenant_id`). No session holds an installation role (T008 §5), so installation-scope experiments are refused (`scope`), not shown to tenants.
