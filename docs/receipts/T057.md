### Rules (decisions an owner or reviewer may challenge)
- **Contract.** It is followed exactly. There is no edition, brand or installation field, so one format serves both editions (R006, R013, R097). The source edition and record counts are gaps, not added fields. C-10 is enforced in code; a schema amendment needs the owner.
- **Versions.** `qw-export-<major>.<minor>`, where `compatibility_version` is the oldest reader that can import. A newer minor is a downgrade: unknown sections are size- and hash-checked, and `.json` ones are also scanned, including for denied ids. They are listed as unsupported and never loaded.
- **Structural allowlist.**
  - **Open sections:**
    - the five T052 learned-state files, with closed key sets per record type derived from the T052 types (`records.json` chosen by `record_kind`, with `subject`, `fact` and case `inputs` nested);
    - `research/evidence.json`, contract Evidence: the exact 13 keys including `coverage`, field types checked, unique `id`s, and tested against `project_contract.schema("evidence")`.
  - Every object is checked recursively; an unknown key, or an object under a scalar, gives `unknown_field`.
  - **Closed** (`section_not_ready`, on export and import): journal, accounts, policies, watchlists and tombstones. Each opens with its store's export function and schema.
  - Key-name and prose heuristics are removed.
- **Value scan.** Defence in depth for high-confidence formats only:
  - PEM in any case (whitespace allowed), and base64 PEM at all three byte offsets;
  - JWTs; `ssh-*`/`ecdsa-*` followed by `AAAA`;
  - AWS `AKIA`/`ASIA`, `gh[opsur]_`, `xox[bap]-`, `[rs]k_live_`, `sk-ant-`, long OpenAI `sk-`/`sk-proj-` (32 or more characters), Google `AIza`, `npm_`, Slack webhooks;
  - URL credentials; `Bearer` tokens of 16 or more characters that contain a digit; `Basic` only when the base64 decodes to a `user:password` (so `Basic 1234567890123456` passes).

  **Free-text fields can still carry anything the scan misses.**
- **Factories.** No seal field: the constructors raise, so `dataclasses.replace` and `copy.replace` fail. A decision whose fields are tampered with, or that is empty, gives `decision`.
- **Licensed evidence (spec §6).**
  - **What a decision records.** Each item's `check_use(user_export)` outcome with its `feed_hash` and `entitlement_hash`, the scope, `at` and jurisdiction, and one omission per denial: `rights:<all deny codes, '.'-joined>:<id>`. Its `decision_hash` covers all of these.
  - **What `build_export` refuses.**
    - A decision for another scope, made after `created_at`, or older than `DECISION_MAX_AGE` (10 minutes).
    - An evidence `id` that is not permitted (`evidence_undecided`).
    - A record whose `rights_profile_id` is not the feed its item was decided on (`evidence_feed_mismatch`). The binding uses `rights_profile_id` because T036 serves the T021 feed id there (`qw_api/research.py`); `source_id` is the T036 source.
    - A denied id in any string value of any section (`evidence_omitted`, checked on import too).
  - **Token rule.** Matching is case-sensitive and unnormalised. An id of 6 or more characters, or of 3 or more mixing letters with digits or punctuation, matches when not preceded or followed by a letter, digit, `_` or `-`: `ref:evd-2`, `evd-2:1` and `evd-2.json` match, but `evd-20` and `x-evd-2` do not. Other ids match only an exactly equal value, because the contract sets no minimum id length and a word-like id (`a`, `data`) would otherwise match prose.
  - **Why 10 minutes.** The decision is made in the same export job, just before the build.
  - **GATE** for the export job increment: the route sets both `at` and `created_at` from the server clock.
- **Import is inert (R051).** Nothing is adopted, activated or reauthorized.

### Rules
- **Writer.** It accepts only an `ExportBundle`, which only `build_export` makes. The layout is `manifest.json`, then files in path order, deflated, mode 0644, fixed timestamp, no extra field or comment, so the same bundle always gives the same bytes. The writer reads its own output back under the same limits.
- **Reader.** Before decompressing anything it checks:
  - size and entry count;
  - per entry:
    - encryption flags;
    - any flag except deflate options and UTF-8 names (`entry_unsupported`);
    - extra fields;
    - symlinks, directories, special entries and executable bits;
    - methods other than stored or deflated;
    - C-10 paths;
  - declared sizes, the ratio above the floor, and duplicate and case-folded names;
  - **layout** (`archive_layout`): local records from offset 0, back to back, then the central directory, then a 22-byte end record that ends the data. This refuses prepended and appended data, polyglots, comments, gaps, overlaps and ZIP64;
  - **local headers** (`local_header_mismatch`): each must equal its central-directory entry.

  Entries are then read with a bound (zipfile stops at the declared size and checks the CRC). Finally the domain `verify_import` runs.
- **Ratio trade-off.** At 100x, repetitive legitimate JSON could be refused, so the ratio applies only above 1 MiB. The size limits bound inflation regardless. Tests show 0.5 MiB of spaces accepted and 2 MiB refused.
- **Windows names.** Reserved names (`CON`, `aux.json`) and trailing dots pass, because nothing is extracted to disk. T058 and T060 must check them before any extraction.

### Rules (decisions an owner or reviewer may challenge)
- **Journal shape: contract LedgerEvent.** Each row is exactly the listLedger item (`ledger_event.schema.json` with project contract 0.4.0), the 15 keys, `postings` `{book_account, commodity, amount}` and `instrument_movements` `{instrument_id, quantity}`. The test validates every exported row against `project_contract.schema("ledger_event")`. It is lossless: the fee, lot policy and supersede link are annotations, an instrument sub-ledger is `<book_account>:<instrument>`, and unit lines use the unit account with the instrument as commodity (the book and unit account names are disjoint). A reversal is `correction`; `status` is `reversed` exactly when its reversal is in the section.
- **Journal checks.** Exact keys (`unknown_field`, `field_missing`). Every row's `tenant_id` must be the manifest scope (`scope_mismatch`). Each row is rebuilt as a `JournalEvent` and re-encoded, and must equal the row. So the `id` fingerprint, idempotency key, movements, annotations, canonical decimal strings and `Z` instants are all checked. Each account is replayed in order through `Journal.post`, as `load_journal` does: a repeat, a broken link, an unbalanced line or `recorded_at` moving backwards is `malformed`.
- **Financial invariants.** `effective_at` (the source's time) and `recorded_at` are exported as stored, and a missing one is `field_missing`. Source records (observations) are not journal entries and are not exported. Claimed executions and predictions have no field here. A row carrying the required keys of `observation`, `execution_report` or `simulated_fill`, or a `virtual` or `simulation_id` key, is `unknown_field`. Virtual holdings are not expressible in this section: a simulation id is never a journal account (0014), and the round-trip test seeds a virtual portfolio that does not appear in the export.
- **Policy shape: each stored version, not contract Policy.** A row is `{policy_id, version, content_hash, label, content}`, the `app.policy_version` columns without `tenant_id` (it is in `content`) and `created_by` (identity). `content` is the draft wire that `content_hash` covers. The contract Policy is not used, for two reasons:
  - it is a lossy view (no allocations, windows, sources, conflicts or exclusions), so the destination could not rebuild a version;
  - its `status`, `accepted_by` and `accepted_at` come from the adoption receipt, and its `adopted` rule requires `accepted_by`. It cannot be written without approval material.

  **Owner decision:** whether a contract-shaped policy section is wanted instead, and with what for adopted versions.
- **Policy checks.** Exact keys at every level, including each limit and allocation. `content.tenant_id` must be the scope. The draft is rebuilt and must give the row's `content_hash`, its `label` and its canonical wire (so `"0.050"` and `"synthetic": 1` are refused). Versions replay through `PolicyHistory.propose` as 1, 2, … with a changed hash each time.
- **Excluded from policies.** Adoption receipts (principal, session, step-up receipt, acknowledgement text, signing time, receipt hash), pause state and `created_by`. The manifest always carries `approval: authority_not_portable`, and the destination re-adopts.
- **Store exports.** `export_journal(tx, page=500)` and `export_policies(tx, page=500)` are read-only and run in the caller's `tenant_transaction` as the tenant role under RLS. Both refuse to run (`tenancy.SnapshotRequired`) unless the server reports the transaction as REPEATABLE READ and READ ONLY, which is `tenant_transaction(snapshot=True)`; the test covers a plain transaction, READ ONLY at READ COMMITTED, and writable REPEATABLE READ. They page by keyset (`list_accounts`, `list_policy_ids`) and read each account or policy through `load_journal` or `load`. So every event id, content hash and receipt hash is re-verified on read, and a tampered row raises `JournalIntegrityError` or `PolicyStoreError("integrity")` instead of being exported.
- **Knowledge time is trusted from the store and from the archive.** The event id covers source content, not `recorded_at`. The tamper test shows the effect: a backdated `recorded_at` that keeps the account's order is exported as stored, undetected. A change that breaks the order fails the replay with the domain `JournalError("recorded_at_order")`, not `JournalIntegrityError`. Within an archive, the manifest hash is integrity, not authenticity, so the same holds on import. Neither the store nor the section detects tail truncation of an account, or reordering of rows with the same `recorded_at`. A per-account head hash or revision count, in a later increment, would close this.
- **For the destination importer (not built).** It must remap or validate `policy_id` (a source-installation UUID that could collide with or name a destination policy) and the account ids. It must treat every free-text value as untrusted: policy sources, warnings and conflict details, and journal source and record ids.
- **Remaining closed sections.** Accounts, watchlists and tombstones stay `section_not_ready`.

### Rules (decisions an owner or reviewer may challenge)
- **Where the chain lives.** `export_manifest.schema.json` is `additionalProperties: false` and has no field for it, so the binding is inside `financial/journal.json`. The body changes from increment 2's bare list to `{"chains": [...], "events": [...]}`. `events` are the same contract LedgerEvent rows. No archive of the increment 2 shape exists outside tests, so the format version stays `qw-export-1.0`; a bare list is now `malformed`. **Owner decision:** whether this change should instead bump the minor version.
- **What it binds.** One closed header record per account, sorted by id: `{account_id, revision, event_count, head}`.
  - `h0 = sha256(json([tag, tenant, account]))`, then `hn = sha256(json([tag, h(n-1), n, id, recorded_at]))` over the account's rows in row order. `tag` is `qw-journal-chain/1`.
  - `id` is the event's content fingerprint, which the row re-encoding already checks. So each step binds content, position and knowledge time.

A gap raises `JournalIntegrityError` even when the remaining rows replay (tested by deleting a row as a tampering owner).
- **What this proves, and what it does not.**
  - **Proves:** integrity against edits to the rows alone. Refused now, each while the rows still replay: a backdated `recorded_at` that keeps the order, a dropped tail, a dropped account, and rows with equal `recorded_at` swapped.   - **Does not prove authenticity.** Anyone who rewrites both rows and header verifies; a test pins this. Detecting that needs a signature (T060, archive authenticity).
  - **Store side.** The store does not bind `recorded_at` either. A tampering owner's backdate that keeps the order is exported as stored, and the chain is computed over it (increment 2's test, kept).
- **Watchlists shape.** Each live list is the contract Watchlist (`id`, `revision`, `name`, `entries`) plus `tenant_id` (the scope check) and `description` (the contract view drops it, so the destination could not rebuild the list). The test validates each row, without the two extras and `needs`, against `project_contract.schema("watchlist")`.
- **Watchlist checks.** Exact keys at every level. `tenant_id` must be the scope. Each entry is rebuilt through the domain (`Entry`, `Condition`, `FeedLatency`, `InstrumentId`) and must re-encode to the row exactly. Entries are in strict instrument order with no repeat. Ids follow the contract pattern and are unique and sorted. `revision` is an int of at least 1. The name is non-empty.
- **Excluded from watchlists.** Deleted lists and their content (no reappearance, R052), the revision history, principals, sessions and idempotency keys. The archive test checks the raw bytes for the deleted list's id and text, every idempotency key, the owner, session, session token, step-up receipt, acknowledgement and receipt hash.
- **Accounts stay closed (`section_not_ready`).** No account, source or mapping store exists. ### Matching at the destination needs the key (decision 104's stated cost)
- **What happens.** Pseudonyms are `HMAC(key, [scheme, tenant, class, id, created_at])`. A destination can verify the imported ledger without any key, but to suppress a deleted record it re-imports it must compute the same pseudonym, and that needs the source installation's key.

  - With another key, `retention.restore` refuses with `key_mismatch` (tested). It never silently matches nothing.
  - So **deleted records stay suppressed at the destination only if the operator carries the key across.** If the key is lost, the ledger still proves itself intact, but no tombstone can be matched to a record.
- **Where the key is declared: in the section, not the manifest.**
  - `export_manifest.schema.json` is `additionalProperties: false` and has no field for it. Putting it in `omissions` or `required_reconnections` would misuse their meaning.
  - So the closed `ledger` header declares `hash_scheme` and `key_id`. `key_id` is a one-way MAC of a fixed label, so it does not reveal the key (T058 5a). The header is bound to the rows: it must equal the recomputed one.
  - The destination checks it up front with `tombstone_wire.check_key(parsed, key)` before applying anything. It takes only the verified `Parsed` from `parse_section`, whose `key_id` equals the header's; a raw header or anything else is `argument`, never a `KeyError` (review finding 3). The results are `key_mismatch` for another key, `key_unavailable` with none, and nothing to check for an empty ledger (tested).
  - **Owner decision (open):** whether the contract manifest should gain a declared field (for example `record_key_id`) in a later contract version, so a destination can see the requirement without opening a section. Recommendation: keep it in the section until the destination importer exists, then decide with its UX.
- **Single chain assumed.** The header describes one chain, which is what 0057 stores (one chain per tenant). Key rotation (a new key starts a new chain, T058) would need a list of chain headers, and therefore a format change. Rotation is not built.

### What the hashes do not prove
They prove integrity, not authenticity, the same limit as the other sections.
- A rewriter who changes a row and recomputes every hash after it (entries, links, seals, checkpoints and the header) is not detected. A test pins this.
- A dropped tail together with its checkpoint is not detected either (also pinned). The stored checkpoint shares the database's failure domain, and the external anchor (T058) is not built.
- Another tenant's ledger retagged with this scope and fully recomputed verifies. Its pseudonyms are keyed by the other tenant, so they match none of this tenant's records (tested). Retagged without recomputing, it is `tombstone_entry`.
- Closing these needs archive signing (T060) and the external anchor.

- **An archive with no policies applies as nothing (chosen, tested).** An empty source tenant moves to an empty destination. Only the audit event is written, so the tenant stays empty and a repeat is a no-op with another audit event, not a refusal.
- **Audit event gap.** `app.audit_event` has no detail or metadata column. Its `correlation_id` (`^[A-Za-z0-9_-]{1,128}$`) does not admit every export id (ID_PATTERN allows `.` and `:`). - **Why the other sections are not applied yet (an insert path is needed: a migration, not built).** Every other store stamps the source's facts again by trigger:

  7. **the chain header** (`ledger_wire.chains`) is recomputed from the stored rows of the tenant's whole journal. It must equal the given `chains` exactly (`QI003`). It binds the tenant id, so another tenant's archive is refused;
  8. **0007's deferred balance and reversal check** runs at once (`SET CONSTRAINTS app.balanced IMMEDIATE`, then `DEFERRED` again). So it refuses inside the caller's savepoint, not at commit.

A runtime session that sets the flag itself is still stamped (tested). It also has no INSERT grant on `account_rev` or `recorded_at`.

  - an open journal writer holds the import off the same way, and once it commits the import is refused `destination_not_empty` (tested).

  - `QI001`, and a deadlock (`40P01`, only possible with a concurrent writer of the tenant) → `destination_not_empty` (tested by injection);

### Rules (decisions an owner or reviewer may challenge)
- **Function contract (as 0060).** Owned by qw_migrate; `search_path = pg_catalog, pg_temp`; `pg_catalog.pg_locks` and `pg_catalog.pg_database` named; EXECUTE revoked from PUBLIC and granted only to qw_app; no tenant argument (the transaction's `app.current_tenant_id()`, forced RLS); no dynamic SQL. The argument is the verified wire section itself, so `destination_import` maps nothing.
- **Refusal order inside SQL:**
  1. no tenant (`QI003`);
  2. the exclusive `import:<tenant>` lock held by this backend, both 32-bit halves, mode and database matched (`QI002`);
  3. no `account`, `account_revision`, `data_source` or `source_mapping_revision` row of the tenant, under that lock (`QI001`);
  4. the section's shape (`QI003`): exactly the four lists; each row exactly its `account_wire` keys, its tenant's id, JSON strings (`revision` a number, `previous_hash` a string or null), a canonical `recorded_at` no more than 5 minutes past `clock_timestamp()` (so an archive cannot put the tenant's knowledge floor in the future). A scalar, null or array element is `QI003` too: a `CASE` keeps the object operators from ever seeing it (an `OR` gave `QI003` only by evaluation order; with the operators first it is `22023`). The rows are gathered with one ordered `jsonb_agg`, not by appending to a `jsonb` value per row. **Every row is checked before any insert**, so a bad row is `QI003` and not a guard error on an earlier row (red run, below);
  5. inserts in one knowledge order: `recorded_at`, then accounts, sources, mappings, account revisions, then archive order. Every foreign key, interval account and chain parent precedes its row;
  6. the replaced guard (`check_violation`): both chains (revision n + 1 naming the previous row hash), the lifecycle (archive once, final), the intervals, and in the import branch `recorded_at` not before the tenant's latest row;
  7. after each insert, the stored row's `row_hash` (sealed by the guard from the kept `recorded_at`) and its `content_hash` recomputed in SQL must equal the archive's (`QI003`).
- **Content hashes in SQL.** `account_wire` digests `json.dumps(..., sort_keys=True, separators=(",", ":"), ensure_ascii=False)`. PostgreSQL's `to_json(text)` escapes exactly `"`, `\`, `\b \f \n \r \t` and other controls as lowercase `\u00XX`, and leaves non-ASCII as is, as Python does with `ensure_ascii=False`. Tested with a name holding quotes, a backslash, a newline, `é` and an injection-shaped string, and a non-ASCII broker (stored and re-exported byte for byte).
- **The stamp is kept only in the definer.** The import branch needs `current_user = 'qw_migrate'` and the transaction-local `app.accounts_import` flag, set only after every row passed step 4 and cleared at the end. A runtime session that sets the flag is still stamped (tested); qw_app has no INSERT grant on `recorded_at` or `row_hash`.
- **The knowledge floor is implied by the sort.** Because rows go in `recorded_at` order, the import branch's floor check cannot fail for this function's own inserts (its mutant survives, below). It is kept as the guard's rule for any other definer insert.
- **The hard gate, for accounts: closed.** Every insert into the four tables shares `import:<tenant>` (the guard) before `source_map:<tenant>`, and `account_store._lock` does the same for every read and write (`register_account`, `add_source`, `remap`, `archive_account`, `load`, `read_accounts`). `grep` found no other writer of these tables or taker of `source_map:` (the domain modules only name the type). Lock order: import, then `source_map`. Two-connection tests: a writer waits for an open import, which completes; the writer then appends after it (no 40P01); an open writer holds the import off (`LockNotAvailable` at a 300 ms `lock_timeout`), and after it commits the import is refused `destination_not_empty`. The cost: an account-store reader now also waits for an import of its tenant.
- **Still open:** watchlists, tombstones, evidence, simulations and the other stores' writers do not take the import lock; their emptiness is still checked in Python before and after the writes (increment 6's limitation).
- **Refusal mapping.** As increment 7 (`QI001`, `40P01` → `destination_not_empty`; `QI003`, `22xxx`, `23xxx` → `apply_verify`), and the refusal now names `financial/accounts.json` when the accounts function raised it.
- **Self-consistency, not authenticity**, as increment 7: a re-sealed, re-chained archive is accepted; signing is T060.
  - **Accepted residual (review M2):** the definer checks no caller role beyond its qw_app EXECUTE grant. A qw_app session that holds the tenant's import lock can therefore import fabricated rows that are self-consistent (hashes, seals, chains, lifecycle, intervals) into an empty tenant. This is consistent with decision 112 and 0060, which accept the same for the journal. Closure: archive signing (T060), verified before the apply.
- **Low follow-up of #238:** the replaced `source_map_guard`, the new function and the replaced `ledger_event_stamp` declare their locals as `pg_catalog` types. 0060's replaced `virtual_account_guard` is unchanged; that half of the follow-up stays open.

Applied migrations are checksummed, so 0060 is not edited: 0062 replaces `app.ledger_event_stamp` with the same body plus, in the import branch only, `QI003` when `recorded_at > clock_timestamp() + 5 minutes`.
