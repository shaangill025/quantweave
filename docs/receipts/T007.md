## Host/VM compatibility notes
- **Platforms:** systrap and ptrace work; ptrace is about 2.5× slower. KVM is unavailable because the VM has no nested `/dev/kvm`.
- **runsc and existing cgroups:** runsc joins an existing cgroup but **does not write limits into it** (observed: a pre-created cgroup kept unlimited memory and pids, and a hog ran unbounded). So the adapter creates `<controller>/qw-sandbox/<id>` itself for memory, pids, cpu and cpuacct, writes the limits, reads them back, and fails the run if any differs. The OCI config therefore carries no `resources`.
- **cgroup v1 only:** the probe blocks with `cgroup_v1_unavailable` when the v1 controllers are absent. The v2 layout (`memory.max`, `cpu.stat usage_usec`, `cpu.max`) is not implemented, because no v2 host was available to test it.
- **Swap:** `memory.memsw.limit_in_bytes` equals the memory limit. If memsw is absent and `/proc/meminfo` shows swap (or cannot be read), setup fails closed.
- **Foreground run:** `runsc run` deletes its own container on exit, so the counters come from the adapter-owned cgroups, which outlive it. A failed `delete --force` is expected after that; only a container still listed by `runsc list` is a cleanup error. Every cleanup step (stop, delete check, drain joins, bundle removal, cgroup removal) runs even if an earlier one fails. Each failure is logged and turns the result into `runtime_error`.
- **CPU time:** `cpuacct.usage` is the whole sandbox, including about 0.12 s of Sentry start-up on this VM. A candidate close to its limit can therefore be reported as `cpu_time`, which fails closed. Exit code 152 has no special meaning: a candidate that exits 152 by itself reads as `exited` with code 152.
- **pids:** a host `pids.limit` of 16 stops the sandbox from booting, because the Sentry threads count against it, so the host pids cgroup gets 256 threads of headroom. Guest processes are bounded by RLIMIT_NPROC inside gVisor: forks beyond the limit fail with EAGAIN in the guest. The host cannot see those failures, so a pids breach is not reliably detected.
- **Scratch, wall time, mounts, state:** `/tmp` is memory-backed, so a large scratch write counts against the memory limit (a 100 MB write at 64 MiB was `memory`). The wall limit is applied in whole seconds, rounded up (`-(-millis // 1000)`), so a run can get up to 999 ms more than `wall_millis`. gVisor adds a writable `/tmp`, `/dev` and `/dev/shm` unless they are mounted explicitly; the adapter mounts `/dev` and `/dev/shm` read-only. `--network=none` pins `<state>/null-netns` once per state dir, and `GVisorRunner.close()` unmounts it. Cgroup writes need host root; the probe blocks otherwise (`runsc_requires_root`).
