### Rules (decisions a reviewer may challenge)
- **Account.** Stores the domain `UnderlyingAccount` (contract `broker` maps to `institution`, `reporting_currency` to `base_currency`) plus the contract `name` (1 to 100 characters) and `analysis_scope`. It is registered once and immutable here. A repeat of the same request returns the stored row. A different request under the same id is `duplicate`.
- **Source.** Stores the domain `Source`, whose `kind` is `SourceKind`; `mirror` marks a Yahoo-style view. A `provider` label (ID pattern) is stored with it. **No credential, token, secret reference or connection state is stored.** The dictionary's `source_connection.secret_reference` and status are deferred until a connection flow exists.
- **Mapping revisions.** Each revision goes through `SourceMap.remap` and is validated before the write.
  - `expected` must be an int of at least 0, else `expected`. It is compare-and-set: a mismatch is `stale`, while the same intervals at `expected + 1` are a retry (`wrote` False).
  - `intervals` must be a sequence of `MappedInterval` values, else `intervals`.
  - At most `MAX_INTERVALS` = 1000 intervals per revision (`too_many_intervals`); 0055's CHECK holds the same limit.
  - The 0055 guard re-checks, for raw inserts: the next revision and the previous hash; exact interval keys and canonical instants; that each account belongs to the tenant; that intervals are sorted, non-empty and disjoint.
- **Knowledge time is stamped by the database** (review finding 1, following 0007's `ledger_event_stamp`).
  - The guard takes the `source_map:<tenant>` lock and sets `recorded_at := greatest(clock_timestamp(), the tenant's latest recorded_at in the three tables)`, whatever was supplied. qw_app has no INSERT grant on `recorded_at` or `row_hash`.
  - **Hash.** The store supplies `content_hash`, its canonical digest of every other column (for a revision this includes `previous_hash`). The guard seals `row_hash = sha256(content_hash || '|' || recorded_at)`, with the instant in `format_instant` form; `seal` is the Python twin. `load` recomputes both, so each stays a function of the stored row, and the chain names the sealed hash, which covers time.
  - **Why split the hash.** Computing the whole hash in SQL would have to reproduce Python's canonical JSON byte for byte (jsonb's text form differs). Computing it after a read-back would need an UPDATE of an append-only row.
  - **Stability.** `load(T)` for a T before the read does not change later, because reads take the lock shared and writes stamp after taking it exclusively. The exception is a snapshot (REPEATABLE READ) transaction whose snapshot predates a write in flight at T.
  - A mapping's valid time (`valid_from`) may lie in the past; its knowledge time cannot.
- **Load.**
  - Every row is re-hashed and each chain is checked (revisions 1..n, previous hash).
  - Rows recorded by `known_as_of` are replayed in knowledge order into a fresh `SourceMap`, and the replay must reproduce each stored revision.
  - Any failure is `integrity`.
  - Hash-only, as in `watchlist_store`: a forger who recomputes the hashes of a chain's latest rows, or removes them, is not detected.
- **Dedupe stays in the domain.** `consolidate` runs on the loaded `SourceMap`. The store does not re-implement or relax it.

### Decisions 102 and 103: broker and account-type text
- **Rule.** `check_display_text` first requires NFC, then `DISPLAY_TEXT`:
  - characters: printable ASCII (`!` to `~`) plus the Latin letters U+00C0–U+00D6, U+00D8–U+00F6 and U+00F8–U+017F (`DISPLAY_LETTERS`). This is Latin-1 Supplement and Latin Extended-A, without × (U+00D7) and ÷ (U+00F7);
  - words separated by exactly one U+0020;
  - 1 to 80 characters (code points).
- **Examples.**
  - Accepted: "Interactive Brokers", "TFSA - Self-directed", "RRSP (spousal) #2", "Crédit Agricole", "Société Générale" and "Caisse Desjardins Épargne".
  - Refused: empty, leading or trailing space, double space, tab, newline, DEL, ESC, and 81 characters (ASCII or accented). Also refused: Cyrillic "І", Greek "Α", NBSP and thin space, zero-width space, LRM, BOM, soft hyphen, fullwidth "Ｉ", ×, ÷, "¿", Latin Extended-B "ƀ", Latin Extended Additional "Ạ", a lone or unattached combining mark, and mathematical bold "𝐀".
- **NFC: normalized at the store boundary, as decision 103 says ("normalized to one canonical form (NFC) before checking").**
  - `account_store.account_from_text(tx, account_id, broker, account_type, reporting_currency)` applies `unicodedata.normalize("NFC", ...)` to `broker` and `account_type` before it builds the domain value. Hashing happens after that, so the stored bytes, `content_hash` and `row_hash` are the NFC form. It is the only store entry point that takes this text; `register_account` takes a domain value, which cannot hold non-NFC text.
  - Anything that bypasses the store is still refused. A domain value built directly from non-NFC text gives `not_nfc` (decomposed "Crédit", or "Å" typed as the Angstrom sign), and 0056's `IS NFC NORMALIZED` refuses a raw non-NFC insert.
- **SQL matches the domain.** `app.account_display_text(x)` is `x IS NFC NORMALIZED AND char_length(x) BETWEEN 1 AND 80 AND x COLLATE "C" ~ '^W+( W+)*$'`, where W is the same class built with `chr()`. qw_app and qw_worker have EXECUTE; PUBLIC does not.
  - The test database is UTF8 with collation C (initdb `--no-locale`, `CREATE DATABASE ... LOCALE 'C'`). The CI service creates its databases the same way.
  - PostgreSQL bracket ranges compare code points. The CHECK uses no character classes and no case folding, and `COLLATE "C"` pins the remaining locale-dependent behaviour on any database collation.
  - `IS NFC NORMALIZED` requires a UTF8 database, and `schema_guard` already requires UTF8.
- **Parity, tested on PostgreSQL 16.**
  - **Every code point:** U+0001 to U+10FFFF except surrogates, alone and between two letters (2,224,126 values) through `app.account_display_text` and the domain. They agree on every value, and the non-ASCII code points accepted alone are exactly U+00C0–U+017F minus U+00D7 and U+00F7.
  - **Raw inserts:** the 39-row parity table also goes through raw qw_app INSERTs into both columns, with the same outcome as the domain.
- **Latin Extended-B and Latin Extended Additional stay out.**
  - Extended-B holds look-alikes of ASCII punctuation and letters: ǀ U+01C0 looks like `|` or `l`, ǃ U+01C3 like `!`, and ƅ, Ʃ and others. It also holds African and Pinyin letters not needed for Canadian or US broker names.
  - Extended Additional (U+1E00–U+1EFF) is mostly Vietnamese and dot-below forms that differ from ASCII by a mark that is barely visible at small sizes.
  - Both can be added by a later decision with a new migration.
- **Residual look-alikes inside the allowed range (recorded, not refused).** These are Latin Extended-A letters the decision allows: ı U+0131 (dotless i), ſ U+017F (long s, looks like f), ĸ U+0138 (kra) and ŉ U+0149, plus Ø and ø against 0. Refusing them would narrow decision 103, so the owner may decide whether to drop them.
- **Existing rows and pre-0056 data.** 102/103 do not only add acceptable values. A value with no spaces of 81 to 128 characters was valid under 0055 and is refused now. `ADD CONSTRAINT` validates every stored row, so 0056 fails rather than keep such a row (`load` would report `integrity`). **No real data may be loaded into 0055's tables before 0056 is applied.** No real accounts are stored yet.
- **Hashes are unaffected.** `content_hash` digests the column values, and `row_hash` seals `content_hash` with `recorded_at`. Neither depends on a CHECK. A test shows a tampered `broker` set to a now-valid value is still `integrity`.
- **One choice (the reviewer may challenge it).** Double spaces are refused. The decision says "single spaces", and "A  B" looks the same as "A B" while being a different value.

### Decision 101: lifecycle stored, status and cash basis derived
- **Storage.**
  - Revision 1 is the `app.account` row, which is active.
  - `app.account_revision` appends revision n + 1 with `lifecycle = 'archived'` (a CHECK) and the previous row hash. For revision 2 that is the account's `row_hash`.
  - The replaced guard requires the next revision and the previous hash, and refuses any revision after an archived one. It also stamps `recorded_at` and seals `row_hash` exactly as in 0055.
  - qw_app has no INSERT grant on `recorded_at` or `row_hash`; qw_worker has SELECT only. The table is append-only for everyone, with forced RLS.
- **Archive is the only transition, and it is final.** There is no unarchive and no second archive (`archived`). No spec text or decision asks for unarchive, and allowing it would make lifecycle a toggle that as-of readers must replay. A user who returns to an account can register a new one.
- **`archive_account(tx, account_id, expected_revision)`** uses compare-and-set.
  - `expected_revision` must be an int of at least 1, else `expected`. An unknown id is `unknown_account`, and a mismatch is `stale`.
  - The same archive at `expected_revision + 1` is a retry (`wrote` False).
  - Archiving does not change mappings or consolidation. A reference's history may still name an archived account, so remap does not refuse it.
- **`load(tx, known_as_of)`.** `AccountRecord` gains `revision` and `lifecycle`, as of `known_as_of`. An account archived later reads `active` at revision 1 before the archive.
  - Every account revision is re-sealed and its chain checked: revision n + 1, the previous row hash, and nothing after an archive. Any failure is `integrity`.
- **`read_accounts(tx, snapshots, as_of, max_age, known_as_of=None)`.** Each read runs the domain `consolidate` on the stored map; nothing derived is stored.
  - `status`: `archived` if archived, else `conflicted` if the consolidation shows a conflict, else `active`.
  - `cash_basis`: the one basis shared by every cash currency, else `unknown`. It is also `unknown` with no snapshot or no cash line. `reconciled_ledger` is never produced, because the domain has no such basis.
  - `source_ids`: the sources whose latest mapping revision names the account.
  - `sizing_blocked` (review finding 1): true when the view blocks sizing or the account is archived. `view` is the raw consolidation and knows nothing of the lifecycle: an archived account with a fresh complete snapshot has an unblocked view. Consumers must read `AccountState.sizing_blocked`.
  - Scopes are not needed for these fields and are not reimplemented.
- **One stricter reading.** `cash_basis` gets a value only when the account's consolidation is `reconciled`. A conflicted, incomplete, stale or no-data account reads `unknown` even when its currencies agree. Such an account is sizing-blocked by the domain, and decision 101 says an "unknown or mixed state fails closed".
- **What is derivable today.** No snapshot or holdings store exists: `import_store` posts transaction files only, and snapshot persistence is T014/T017. `read_accounts` therefore takes the snapshots the caller holds. A route or the T057 export that has none passes `()`. Every account then reads `status` `active` (or `archived`), `cash_basis` `unknown`, view `no_data` and `sizing_blocked` true.
- **Who reads sizing permission today.** Two domain functions take `AccountView` mappings directly: `qw_domain.scopes` (`_spendable`, the gaps in `apply_scope`) and `qw_domain.allocation` (`ACCOUNT_UNAVAILABLE`). Neither has a caller that goes through `read_accounts`: no adapter, API or worker code calls `consolidate`, `apply_scope`, `spendable_cash` or allocation with stored accounts. The store's only reader of sizing permission is the new `AccountState.sizing_blocked`.
  - Gate (T017/T026 wiring): whoever first feeds `read_accounts` into scopes or allocation must leave out, or block, every account whose `AccountState.sizing_blocked` is true. A view-only check would size an archived account.

### Gates recorded for T057 and the API (from the review)
- **(Medium) `status` hides the data state.** `status` reads `active` when the view is `no_data`, `stale` or `incomplete`, and the contract `status` enum has no `unknown`. So the T057 accounts export and the account routes must:
  - export the view's data state (`reconciled`, `conflicted`, `incomplete`, `stale` or `no_data`) and `sizing_blocked` alongside `status`;
  - never show an account with no snapshot as healthy, which T057 tests must assert.
  - The owner may later decide to add a contract state.
- **(Low) `source_ids` ignores interval dates.** It counts the latest revision of each (source, reference) whatever its interval dates, so a source whose only interval naming the account has ended still counts. The T057 mapping must state this.
- **(Low) `source_ids` type.** The data dictionary types `source_ids` as `uuid[]`, but the store uses text ids (`ID_PATTERN`). T057 must decide which.
- **(Low) Retries and principals.** An `archive_account` retry cannot be told apart from another principal's identical archive. This is part of the principal-attribution gap.
